## 与计划的偏差

- **第 0 步没做备份**：卡上都是测试录音，用户决定不备份（`pull` 下到一半停掉）。这削弱了恢复保障，不影响对删除行为的观察。
- **S2 的大小基线**：原定与备份比对，改为与同步时卡上报的大小比对（日志 `rx 90`）。只能说明大小没变，不能说明内容哈希一致。
- **S5 的 bondId**：原定用卡上原始值检索。原始值没能自动解析，改为人工逐行检查诊断文件，不是脚本实测。
- **S1 的提交时序**：日志没有单独的「录音已提交」记录，用诊断信息里该轮同步成功结束（`idle ... failures 0`）作为间接证据。
- **S6 的范围**：原始 `card-debug.log` 有 121322 行、10077582 B（sha256 `ff0341074b390de6b17465766627b19a4d550e0b52b0d6dc33cdd1d28da245e2`），入库的只是本次时段 554 行（原文第 120769 行起）。整份原文的计数命令：`grep -cE "tx (93|94|B0|B1) " card-debug.log` → `0`。
- A 实测 17 s、B 15 s（poki 操作延迟），不影响判据。

### S4 修复与复测

根因：P08 的行来自 `CardSession.pairedDevices`，它只在配对、解绑、改名和扫描页消失时重读；`SyncEngine.currentDevice()` 每轮把 `lastSeenAt` 写进库，却不更新这份缓存。P07 的电量、存储读 `session.cardInfo`，不受影响。

修复：`SyncEngine` 每轮保存设备行后调用 `onDeviceSaved`，`CardSession` 在回调里重读配对列表（不调 `refreshDevices`，避免忘卡、识别卡的副作用）。单元测试 `HomeModelTests.lastSeenFollowsEachPass`：没有新文件的一轮之后 P08 时间前进；去掉修复时失败。

复测（同一手机和卡，新 Debug 包），日志 `s4-retest.log`（30 行）：

| 时间 | 操作 | P08「上次连接」 |
|---|---|---|
| 13:06 | 启动后打开 P08（未连接） | 12:46 |
| 13:07:20 | 唤醒卡，连接后自动同步一轮（`tx A1`、`tx 90`） | 打开 P08：已连接 · 13:07 |
| 13:09:32 | 下拉同步，没有新文件（`tx A1`、`tx 90`） | 打开 P08：已连接 · 13:09 |

全程没有进扫描页。第一次下拉（约 13:08）没有触发同步（日志无命令，poki 滑动未被识别为下拉），因此 P08 仍为 13:07，不计入判定。

## 结论

删除路径在真卡上没有回归：「同步后删除」只删已存入手机的录音，本地删除过的录音（A 和 2 个旧文件）留在卡上；全程没有发禁发命令。S4 的「上次连接」缺陷已在本 PR 修复并复测通过。

S1～S6 在上述偏差范围内通过，PR #46 可以合并。偏差均已列出：没有备份、S2 只比大小、S5 的 bondId 为人工检查。
