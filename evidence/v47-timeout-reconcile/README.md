# #47 录音命令超时对账：命令未回包时读 `0x56` — 2026-11-09

## 目的

#47 的做法是：录音命令（`0x51` 开始、`0x52` 暂停、`0x53` 继续、`0x50` 停止）等不到回包时，App 读一次 `0x56`，按卡报告的状态判断命令是否已生效（`CardSession.recordingCommand`）。这个做法只在模拟卡上测过。本次在真卡上验证它依赖的前提：**录音命令还没回包时，卡也会回答 `0x56`，而且报告的是命令执行后的状态。**

## 环境

| 项 | 值 |
|---|---|
| 主机 | Mac15,12，macOS 27.0，Python 客户端 + bleak 3.0.2 |
| 代码 | `client/probe_m1.py reconcile`，基于提交 `1579b91` 加本次改动 |
| 卡 | 固件 v1.50，已配对，加密开启；与 #34 为同一张卡 |

按 ADR-006，日志不含 `sn`、`btaddr`、`bondId`（本次未发 `0x80`/`0xA1`，已全文检索确认命中 0 次）。测试新增 1 个录音文件 `20261109163736.opus`（约 7 s），未下载、未删除任何文件。

## 命令

```
A=853BE462-3927-35DC-A23E-F592DFD35491   # macOS CoreBluetooth identifier, not the card's btaddr
python probe_m1.py --address $A --out ../evidence/v47-timeout-reconcile reconcile
```

每一步：发录音命令 → 立即发 `0x56`（不等命令回包）→ 最多等 8 s → 1 s 后再读一次 `0x56`。每步之间间隔 3 s。原始日志见 `reconcile.jsonl`。

## 判据

每一步同时满足：

1. 命令发出后紧跟的 `0x56` 在 8 s 内有回答（`status_answered_in_flight`）；
2. 1 s 后再读的 `rec` 等于 App 期望的目标值（`settled_reached`）：开始 1、暂停 2、继续 1、停止 0。

## 结果：通过（4/4）

| 步骤 | 目标 `rec` | 先到 | 命令回包 | 紧跟的 `0x56` | 1 s 后 `0x56` |
|---|---|---|---|---|---|
| 开始 `0x51` | 1 | 回包 0.302 s | `{"name":"20261109163736.opus"}` | 0.331 s，`rec 1` | `rec 1` |
| 暂停 `0x52` | 2 | 回包 0.059 s | `01` | 0.119 s，`rec 2` | `rec 2` |
| 继续 `0x53` | 1 | 回包 0.058 s | `01` | 0.117 s，`rec 1` | `rec 1` |
| 停止 `0x50` | 0 | `0x56` 0.057 s | `01`（0.117 s） | `rec 0`，期间共收到 2 个 `0x56` | `rec 0` |

- 紧跟的 `0x56` 每次都有回答，而且 `rec` 已经是目标值，比判据要求的「1 s 后」更早。
- 停止那一步收到两个 `0x56`（都是 `rec 0`）：一个是卡停止后的主动推送，一个是对本次查询的回答。两者一个在 `0x50` 回包之前、一个在之后，从日志无法分清哪个是哪个，不影响结论。
- 卡看起来是按顺序处理命令的：`0x56` 的回答总在前一条命令执行之后。

## 局限

- 本次卡每次都回了命令回包，没有真正出现「回包丢失」。蓝牙层面的丢包没法在客户端故意制造；本次验证的是对账依赖的卡端行为，App 在超时后的处理由单元测试覆盖（`HomeModelTests`，`FakeCard.dropReply` 等）。
- 未验证：卡在忙于传文件（`0x70`）时收到录音命令的情况。

## 结论与回填

| 项 | 结论 | 回填 |
|---|---|---|
| 录音命令后读 `0x56` 对账 | 可行；卡在命令未回包时也回答 `0x56`，报告的是执行后的状态 | `PROTOCOL.md` §4.3 `0x56` 一行 |

适用范围：固件 v1.50，单张卡。其他固件版本见 #8。
