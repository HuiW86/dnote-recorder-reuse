## 1. 背景与目标

### 1.1 问题域

D·NOTE 录音卡的硬件完好，但可用性依赖一套厂商后台：账号鉴权、设备绑定、云端转写与存储、会员、分发。当前这套后台已经失效：

- 登录依赖短信验证码，验证码已经收不到；
- `api.dreamenote.cn`、`me.dreamenote.cn` 的 HTTPS 证书均已过期（2026-11-05 实测），App 的所有云端请求在 TLS 握手阶段就失败；
- 官方 App 把**配对放在登录之后**，所以登录一断，整张卡不可用。

竞品分析表明这不是个例：Plaud、钉钉 A1、TicNote、Omi 都把配对放在登录之后（见 `competitor-analysis.md` §2）。

### 1.2 目标

做一个替代产品（App + 后端），让这一批卡的持有者无需官方账号和官方云，恢复官方 App 的产品形态：配对、录音、同步、播放、转写、AI 总结、实时转写、笔记、导出、换手机恢复。范围按 `official-app-analysis.md` 的 **C 方案**（接近全复刻，去掉电子名片）。

### 1.3 第一原则（已确认）

> **设备功能离线优先**：配对、录音控制、把录音同步到手机、播放、导出原始音频，不依赖登录和网络。登录只用于转写、AI 生成、AI 对话和云同步。

这是本设计区别于官方方案的根本之处，后文所有分域都以此为界。

—— **补充（2026-11-18，ADR-009）**：「登录只用于转写、AI 生成、AI 对话」只对走我们后端的那条路成立。AI 能力现在有三条路：本机转写（不登录、不联网）、用户自配服务（不登录，App 直连用户选的服务商）、账号加后端。见 §4.10；后端停止服务时怎么办见 §4.11。

### 1.4 成功判断

全部可证伪，验证方法见 §7.1：

1. 新用户不注册、不联网，能完成配对、录音、同步到手机、播放、导出原始音频。
2. 登录后，一段录音能自动完成"上传 → 转写（区分说话人）→ AI 总结"，结果回到 App。
3. 实时录音时，App 上能持续看到转写文字。
4. 换一台手机登录同一账号，录音、转写、总结、笔记、已配对设备都能恢复。
5. 后端或网络故障时，第 1 条不受影响，转写任务排队，恢复后自动补做。
6. 全程不触发任何不可逆的设备状态变更（尤其是固件）。

## 2. 范围与约束

### 2.1 覆盖

账号与鉴权、设备登记、录音接入与存储、转写与 AI 生成、实时转写、云同步、用量统计，以及 OTA、加密密钥的处置策略和卡 WiFi 直传通道的接管。

### 2.2 不覆盖

- 商业闭环：收费、订阅、成本、合规，按决定暂不考虑；后端保留用量统计，用于限流和控制 API 成本。
- 电子名片（官方 `/business-card/*`，走 `me.dreamenote.cn`）。
- 改动设备硬件与出厂固件（刷自有固件属 L3，另案）。
- 与官方云的互通或账号迁移；**曾被官方 App 绑定过的旧卡接管**，按决定暂不考虑。

### 2.3 硬约束（来自既有协议和设备，不可协商）

| 约束 | 来源 | 对设计的影响 |
|---|---|---|
| 设备只认既有 BLE 帧协议 | `PROTOCOL.md` §3 | 只能在既有命令集内编排，不能要求设备出现新命令 |
| **录音需要先配对** | 真机（2026-11-05；#38 更正） | 未配对时 `0x51` 录音回 `{"name":"NULL"}`、`0x94` 格式化失败；`0x90` 列表、`0x70` 下载、`0x91` 删除仍可执行（#38，测的是一张设过密钥的 v1.50 卡，从未设过密钥的卡未验证），所以 App 在同步前自己用 `0xA1` 确认本机绑定。配对（`0xA2` 设密钥 + `0xA0` 绑定）在同一连接内生效，不需要重连。配对必须放在 App 的离线路径里 |
| 设备主动联网能力有限 | `0x88` 热点、`0x89` 上传地址 | 设备没有通用 HTTP 客户端；卡直传需要适配设备既定的上传格式（未逆向） |
| 音频为 16kHz 单声道 Opus，40 字节/帧 | `PROTOCOL.md` §6.1，真机确认 | 转写输入格式固定；说话人区分只能靠声纹 |
| 加密派生用的常量硬编码在固件和 App 里 | `PROTOCOL.md` §6.2 | 解密密钥可离线算出；常量本身改不了 |
| **蓝牙传输慢** | 真机：22,060 字节约 1 秒（单次样本） | 约 20KB/s 量级；1 小时录音约 7MB，蓝牙需数分钟。长录音必须有 WiFi 快传（`192.168.88.1:6718`，~~TCP 协议未逆向~~ —— **更正（2026-11-11）**：协议已还原并真机实测，见 `PROTOCOL.md` §7、#6、`evidence/v2-fasttransfer/`） |
| USB 存储在新版 macOS 上挂载不了 | 真机 | USB 不作为 App 的接入路径 |

> 更正：原方案和 `PROTOCOL.md` §7 写的"BLE 全速约 1MB/s"有误，1MB/s 是 USB 全速的量级。

## 4. 方案设计

### 4.1 总体结构：App 本地域 + 后端云域

| 域 | 位置 | 职责 | 断网或未登录时 |
|---|---|---|---|
| 设备通道 | App | 扫描、配对、录音控制、设备设置、蓝牙下载、WiFi 快传、实时音频接收 | **正常** |
| 本地录音库 | App | 原始音频、元数据、文件夹、回收站、笔记草稿、绑定码 | **正常** |
| 播放与导出 | App | 解密、OGG 封装、播放、导出原始音频 | **正常** |
| 同步引擎 | App | 上传音频、拉取转写和总结、元数据双向同步、断点续传 | 排队，恢复后自动补做 |
| 账号与鉴权 | 后端 | 登录、token、注销 | 未登录时 AI 功能置灰并引导登录 |
| 设备登记 | 后端 | 备份绑定码，支持换手机恢复 | 不影响已配对设备的使用 |
| 存储 | 后端 | 音频对象存储、元数据数据库、检索索引 | — |
| 转写与 AI | 后端 | 转写任务、AI 生成、AI 对话、实时转写 | 任务排队 |

设备通道、本地录音库、播放与导出三域在 App 内闭环，保证 §1.3 第一原则；后端只承担"锦上添花"的 AI 能力和云同步。

—— **补充（2026-11-18，ADR-009）**：表里「转写与 AI」只有后端一行，已经不完整。App 内另有两个域，都不经过我们的后端：本机转写（M1.5 X9，`Transcription` 模块，断网或未登录时**正常**）和用户自配服务（M2 X11，`Assistant` 模块，断网时不可用，未登录时**正常**）。见 §4.10。

### 4.2 录音怎么进入系统：三条路径

**路径 A：手机中转（主路径）**
卡 → 蓝牙或 WiFi 快传 → App 解密并存入本地库 → 登录后由同步引擎上传。
- 小文件走蓝牙；大文件自动切换 WiFi 快传（竞品通行做法）。iOS 上连卡的热点 `FastUpload` 需要用系统热点配置接口，列入技术验证。
- 卡上的文件**确认已经存入本地库后才删除**；同步按文件名和大小做幂等、可续传（借鉴 Omi 的教训）。

**路径 B：卡 WiFi 直传（可选，待验证）**
用 `0x89` 把卡的上传地址指向我们的接入网关，卡连上 WiFi 后不经过手机直接上传。
- 适用：固定场景、长时间录音。
- 前提：上传格式与字段真机确认（§7.2 假设 H3）。不成立就退回路径 A。

**路径 C：实时录音**
App 发 `0x51 [1]` → 卡通过 `0x68` 推 Opus 音频块 → App 解码为 16kHz PCM → WebSocket 推到后端 → 流式转写结果推回 App。
- 启动用 `0x51 [1]`，不需要 `0x54`；`0x68` 是明文 Opus，4 帧/包、50 帧/秒（H2 已验证，见 §7.2）。
- 断线时 App 本地保留音频，重连后补传（借鉴 Omi）。

三条路径最终都汇入同一套存储和转写流水线。

### 4.3 配对与账号

**配对完全在 App 内离线完成**，流程照搬官方，把云端那一步换成本地生成：

1. 连接，`0x80` 取 `sn`；先用 `0xA1` 查询绑定，已绑定本机则直接结束，不发写命令（#38）；再 `0x87` 校时
2. `0xA2`：`[1] + HMAC-SHA256(DEVICE_KEY_SECRET, sn)`，开启加密
3. `0xA0`：`[1] + 本地随机生成的 16 字节绑定码`
4. 用 `0xA1` 查询确认绑定生效（同一连接内即生效，不需要断开重连：H1 已验证，见 §7.2）
5. 绑定码存入本地；登录后备份到后端"设备登记"模块

官方新卡绑定时会先发 `0x94` 格式化；我们不照搬，避免用户误删录音（真机上未配对时格式化也会被拒）。

**账号参考官方 App**，但位置从"配对之前"挪到"使用 AI 功能之前"：

- 登录方式：手机号 + 短信验证码、邮箱 + 密码；短信服务失效时邮箱可作后备（官方正是坏在短信这一环）。
- 账号页面：登录、注册、验证、找回和修改密码、App 内注销（苹果审核要求）。
- 第一次登录时，本地已有的录音和已配对设备合并进账号。

| # | 模块 | 作用 | 对应官方接口 |

| 9 | 用量统计 | 记录转写时长和大模型调用量，限流、防滥用 | 部分对应 `/subscription/usage` |

### 4.5 转写与 AI 流水线

```
原始音频（OGG/Opus）→ ASR + 说话人区分 → 结构化（分段、说话人命名）→ AI 生成（总结、金句、思维导图、标签）→ 检索索引
```

- **原始音频是唯一的事实来源**，后续产物都能重算；以后换更好的模型可以批量重跑。
- **采集与处理解耦**：音频先落在 App 本地；上传和转写异步排队，失败自动重试。
- **ASR 做成可替换的**：云厂商 API 和自建 FunASR 走同一个接口，技术验证阶段对比后选默认（§5.1）。
- **大模型做成网关**：提示词模板服务端管理，模型可切换。

### 4.6 App 与后端的接口边界

接口契约见 [`prd.md`](prd.md) §7，这里只定边界：

| 类别 | 形式 | 说明 |
|---|---|---|
| 鉴权 | HTTPS + Bearer token，access/refresh 双 token | 未登录时 App 不调用任何后端接口 |
| 资源接口 | REST + JSON | 用户、设备、录音元数据、转写、总结、笔记、文件夹、模板 |
| 文件上传 | 预签名 URL 直传对象存储，支持分片续传 | 大文件不经过应用服务器 |
| 异步任务 | 提交返回任务 id；状态 `queued → running → succeeded / failed`；App 轮询或接收推送 | 转写、AI 生成 |
| 流式返回 | SSE | AI 对话 |
| 实时转写 | WebSocket，URL 显式带 `codec`、`sample_rate`、`language` | 借鉴 Omi |
| 同步 | 以记录 id + 更新时间做增量同步，冲突以最后修改为准 | 细节在契约文档中定 |
| 错误码 | 统一结构：业务码 + 消息 + 可重试标记 | — |

### 4.7 iOS 专项

| 项 | 风险 | 处置 |
|---|---|---|
| 后台蓝牙 | iOS 对后台扫描和长连接有限制，可能影响"自动同步" | 技术验证 V7（#7）；不行就退回"打开 App 时同步" |
| 连接卡的热点 | 需要系统热点配置接口及相应权限 | 技术验证 V7（#7）；付费开发者账号 |

| 官方 iOS 版 | 只拿到安卓包；官方代码含苹果内购接口和 iOS App Group 配置，推断 iOS 版用的是同一套代码 | 分析结论按适用于 iOS 处理 |

### 4.8 OTA：默认不提供

协议有固件升级命令（`0xB0`/`0xB1`），APK 里也有官方固件文件。但本设计**默认不做 OTA**：

- 设备当前固件（v1.50）功能完好，OTA 不是恢复可用性的必要条件；
- 刷写失败可能变砖，且不可逆，违反成功判断第 6 条；
- APK 内固件的版本、完整性、签名都未分析。

保留姿态：先分析 APK 内固件（版本号、是否比 v1.50 新、有无签名），只在出现明确的修复需求时，另立专项评估。

### 4.9 加密密钥：沿用派生密钥

- 默认开启加密，密钥用 `HMAC-SHA256(DEVICE_KEY_SECRET, sn)` 离线算出，和官方一致；App 解密不需要后端。
- 不重设为自选密钥：重设后卡上已有文件按原规则解不开，收益不明显。
- 解密在 App 内完成，上传到后端的是解密后的 OGG。

### 4.10 第二条 AI 路径：用户自配服务（2026-11-18 补充）

本节是新增内容，不改上文。依据 ADR-009（2026-11-16 接受）和 `features.md` X11（M2，P0）。

**已定（ADR-009）**

- AI 能力有三条路：本机转写（X9，M1.5）、用户自配服务（X11）、账号加后端（§4.4、§4.5）。后两条是并列的主路径，第一次用 AI 功能时让用户选；两条路功能对等。
- 用户自配服务：用户在设置里填一个兼容 OpenAI 接口的地址、模型名和密钥。App 直接调用这个服务，不经过我们的后端，不需要账号。转写走 `/audio/transcriptions`，总结和对话走 `/chat/completions`。
- 密钥只存 iOS Keychain，不进数据库、偏好设置和日志。App 不内置任何由我们持有的服务商密钥（§2.4 已更正）。
- 提示词只有一份来源：随 App 内置一份，后端用同一份；后端更新后 App 可以拉取并缓存。两条路共用解析代码，后端的转写与总结接口保持与 OpenAI 兼容接口相近的输入输出（`prd.md` §7）。
- 硬规则 3 不受影响：联网代码放在单独的模块，设备模块不依赖它；`scripts/check-m1-rules.sh` 继续检查设备模块不联网。
- 提前交付：这条路不需要账号、后端、备案和短信通道，可以先于后端上线。

**现状（2026-11-18）**

- 只做了 ReviveKit 里的核心，在分支 `claude/eloquent-feynman-hmfo1r` 的提交 `f800696`，**还没有合并，也没有界面**（设置页、选择页、结果页都还没做）：
  - `Assistant` 模块：`ChatClient`（`/chat/completions`，有密钥时带 `Authorization: Bearer`，温度 0.2，可要求 JSON 输出，超时 300 s）；`Summarizer`（场景、标题、摘要、分栏要点、待办、标签、人物；文字稿超过 9000 字时先按约 6000 字一段分段压缩，再整体总结；没配置服务时有一个按关键词的粗略兜底）；`KeychainKeyStore`；`ServicePreset`（12 家 `/chat/completions` 服务商的地址，另有 4 家 `/audio/transcriptions` 的，后者**还没有用到**）。
  - 设备模块和 `AppModel` 不依赖 `Assistant`；`Assistant` 不在 `check-m1-rules.sh` 的不联网名单里，它是唯一允许联网的模块。
  - 提示词和场景分类改编自 beanpod（MIT，见 `NOTICE`），目前只在 App 里，后端还不存在，「后端用同一份、App 拉取缓存」都还没有实现。
  - 转写走 `/audio/transcriptions` 还没有实现：现在能送去总结的文字稿只来自本机转写（X9）。
  - Keychain 项可在首次解锁后读取（`kSecAttrAccessibleAfterFirstUnlock`），没有设 `ThisDeviceOnly`，也没有设 iCloud 钥匙串同步：会随加密的本机备份迁到新手机，不会经 iCloud 钥匙串同步。这是现状描述，是否合适待定。

**哪些数据离开手机，发给谁**

| 路径 | 发出的数据 | 发给谁 | 不发什么 |
|---|---|---|---|
| 本机转写（X9） | 无 | — | 录音和文字都留在手机上（强制离线识别） |
| 用户自配服务：总结（已有核心代码） | 文字稿全文（或分段）、录音时长、用户选定的场景（如有）、模型名、提示词；请求头里是用户的密钥 | 用户填的那个地址，即用户选的服务商；**不经过我们**，我们也看不到 | 不发音频、卡的 `sn`、设备信息、账号信息 |
| 用户自配服务：转写（计划） | 录音音频（解码后的音频文件，格式待定） | 同上 | 同上 |
| 账号加后端（M2） | 音频、元数据、转写和总结结果 | 我们的后端，再由后端发给我们选的 ASR 和大模型服务商（§4.5、§5.1） | — |

- 服务商怎么保存、是否用来训练，由用户和该服务商之间的条款决定。界面和隐私政策要写明「录音或文字会发到你选的服务商」（ADR-009 后果一节）；`release/privacy-policy.md` 在界面做好时补。
- 地址由用户填，可以是任何地址（包括局域网里自己架的服务）。App 不校验它是否「可信」，只在请求失败时如实提示（`AssistantError`：未设置、HTTP 错误码、回答看不懂、连不上）。

**待定（提案，未决定）**

- 第一次用 AI 时的选择页怎么写、默认推荐哪家：随 M2 页面规格定。
- 只配了总结、没配转写时，文字稿来自本机转写还是要求用户再配一个转写服务。
- 提示词由后端下发后，App 用哪一份：建议以 App 内置版本号为下限，后端只能下发更新的版本。

### 4.11 停服预案（2026-11-18 补充）

本节是新增内容。对应 `competitor-analysis.md` §4 第 8 条（「停服或迁移时给出明确的导出窗口和公告机制」，原记为后期事项），ADR-009 把它提前到设计里。起因就是 D·NOTE 本身：官网还在，后台静默失效，没有公告、没有导出窗口（`competitor-analysis.md` §2 第 3 条）。

**已定的部分**：下面「继续可用」一栏，是硬规则 3 和 ADR-009 已经保证的结果，不需要停服时再做什么。**其余都是提案**，要在 M2 上线前定下来，并写进公开的服务条款或隐私政策。

**后端停止服务后**

| 继续可用（App 内闭环） | 停止 |
|---|---|
| 配对、录音控制、蓝牙同步、播放、导出 OGG 和 M4A（硬规则 3：这些代码路径里没有后端调用） | 账号：注册、登录、找回密码、App 内注销 |
| 本地录音库：最近删除、重命名、重点、已有的文字稿和总结（都存在手机上） | 云同步与换手机恢复（N1）；后端里的录音、文字稿、总结副本 |
| 本机转写（X9，前提是 #67 测量后保留） | 设备登记（A4b）：换手机后不能从账号恢复绑定码，只能在新手机上重新配对（卡已被旧绑定码绑定时，按 `product-spec.md` §3.1 确认重新绑定，离线可完成） |
| 用户自配服务（X11）：总结、对话；转写在实现 `/audio/transcriptions` 后也可用 | 后端代跑的转写、AI 生成、AI 对话、实时转写（F1、G1、G3、H1 的后端那一半）；排队中的任务不会再完成 |
| App 内置的提示词 | 提示词更新、模板下发、意见反馈（O1b） |

**停服前要做到的（提案）**

1. **提前公告**：至少提前 90 天，在 App 内（启动时一次性提示加设置页常驻说明）和公开页面同时公告，写明停止日期、哪些功能停、哪些不受影响（上表）。90 天是提案；参照 Humane 只提前约 10 天的反例（`competitor-analysis.md` §2 第 3 条）。
2. **导出窗口**：公告期内后端照常运行，用户能把存在后端的东西全部取回：音频、文字稿、总结，用开放格式（音频 OGG/M4A，文字和总结用 Markdown 或 JSON）。前提是 `competitor-analysis.md` §4 第 6 条的「用户自助全量导出」在 M2/M4 就做好，而不是停服时临时做。
3. **引导换路**：公告里告诉用户可以改用本机转写或自配服务；App 提供一键切换到自配服务的入口（X11 的设置页）。
4. **不让 App 坏掉**：停服前发一个 App 更新，去掉或隐藏账号入口和后端相关的界面；更新之前，后端不可达时 App 也必须照常工作（§7.1 第 5 条），不能因为域名过期或证书过期卡住任何界面——这正是 D·NOTE 失效的方式（§1.1）。
5. **数据删除**：停止日期之后删除后端里的用户数据和设备登记，删除完成后公告。
6. **可选**：把后端代码公开，让愿意的人自己部署（参照 Omi，§5.4）。是否这样做，到时视依赖的云服务和许可再定。

验证：§7.1 第 5 条（关停后端后离线功能不受影响）在 M2 验收时测；上表「继续可用」一栏每一项都应在同一次测试里覆盖，包括自配服务在后端关停时照常工作（`test-spec.md` §6 的 M2 行）。

## 5. 方案选择与理由

### 5.1 转写：云厂商 API 还是自建 FunASR

| 维度 | 国内云厂商 ASR（阿里云、腾讯云、火山引擎、讯飞等） | 自建 FunASR（部署在我们的服务器） |
|---|---|---|
| 准确率与说话人区分 | 通常较好，需实测 | 依模型和算力，需实测 |
| 流式实时转写 | 普遍支持 | 支持，需自己运维 |
| 成本 | 按时长付费 | 一次性算力 + 运维 |
| 运维 | 低 | 高 |
| 数据 | 经过第三方 | 留在自己的服务器 |

**结论在 M2 前置任务（ASR 选型）和 M3 前置任务（流式 ASR）中定**：用真卡录音对比 2～3 家云厂商和 FunASR，看中文准确率、说话人区分和流式延迟。架构上两者走同一接口，可以随时切换。

### 5.2 账号放在哪一步

| 方案 | 代价 |
|---|---|
| 配对之前（官方、Plaud、钉钉、TicNote、Omi 的做法） | 登录一断整张卡不可用，即 D·NOTE 失效的原因 |
| **使用 AI 功能之前（采用）** | App 要多做本地录音库，以及登录前后两种状态的设计 |

### 5.3 后端技术栈

后端语言、框架、数据库、任务队列、云厂商在技术选型文档中定。选型要点：国内云厂商 ASR 和大模型 SDK 的支持、异步任务和 WebSocket 的成熟度、对象存储直传。

已定（2026-11-06，#26）：Python + FastAPI + PostgreSQL，任务队列放在 PostgreSQL 里（[ADR-002](adr/002-backend-python-fastapi-postgres.md)）；云厂商腾讯云（[ADR-003](adr/003-cloud-tencent.md)）。App 用 Swift 原生（[ADR-001](adr/001-ios-app-native-swift.md)），先用 TestFlight 分发（[ADR-004](adr/004-distribution-testflight.md)），代号 Revive（[ADR-005](adr/005-naming-codename.md)），显示名「闻笺」（[ADR-008](adr/008-display-name-and-icon.md)）。

### 5.4 先例

- **Valetudo**：为扫地机器人提供厂商云的本地替代，本地优先、云可弃。差异在于它替换的是设备固件里的云客户端，我们在不改固件的前提下接管协议外侧。
- **Omi**：开源的 AI 录音设备，App + 后端架构、实时转写 WebSocket、可替换的 ASR 都可借鉴；它把登录放在配对之前，是我们要避开的做法。
- **社区自救项目**：钉钉 A1、Limitless 都有社区工具绕开官方 App 直连蓝牙，说明这类需求真实存在。

## 7. 验收、风险与回退

### 7.1 验收标准（对应 §1.4）

| # | 判断 | 验证方法 | 通过线 |
|---|---|---|---|
| 1 | 离线可用 | 新装 App，不注册，开飞行模式（蓝牙开），完成配对、录音、同步、播放、导出 | 全部成功 |
| 2 | 转写与总结 | 登录后录 5 分钟多人对话 | 自动出现带说话人的转写和总结 |
| 3 | 实时转写 | 实时录音 1 分钟 | App 上持续出现文字 |

**待验证（构成风险）**：

| 编号 | 假设 | 影响 | 验证 | 结论 |
|---|---|---|---|---|
| H1 | 配对要断开重连才生效 | 配对流程设计 | V3（#5） | **否定**；同一连接内即生效，不需要重连，见下 |
| H2 | `0x54` 是两段式启动，能稳定收到 `0x68` | 实时录音整体 | V1（#4） | **成立（启动方式不同）**；`0x51 [1]` 即可，`0x54` 不需要，见下 |

| H4 | WiFi 快传的 TCP 协议能从官方 JS 逆向出来 | 长录音体验 | V2（#6） | **部分否定，结果更好**；V2 实测快传约为蓝牙 33 倍，见下 |
| H5 | 配对后按键录音能产生文件，且能被 App 发现 | 卡上按键的产品体验 | V3（#5） | **成立，带一个约束**；录音中列表为空，见下 |
| H6 | iOS 能连卡的热点，后台蓝牙满足自动同步 | iOS 上的同步体验 | V7（#7）、#21 | **成立，带一个硬约束**，见下 |

#### H2 结论（2026-11-06，#4）

**实时录音成立，但不是靠 `0x54`。** 在 Mac 上（bleak）对已绑定、加密开启的卡（fw v1.50）试三种启动方式：

| 启动方式 | `0x68` 包 | 帧偏差 | 断开 |
|---|---|---|---|
| `0x51 [1]`，10 s | 116 | 0.92% | 否 |
| `0x54 [1]`，10 s | 0（卡无任何响应） | — | 否 |
| 官方流程（0.5 s 无 `0x68` 再补发 `0x54`），10 s | 124 | 0.79% | 否 |
| `0x51 [1]`，60 s × 3 | 743 / 743 / 744 | 0.14% / 0.14% / 0.15% | 否 |

通过线（连续 3 次 × 60 s 不断开，帧偏差 ≤ 5%）满足。

- `0x68` 每包 168 B = 8 B 头 + 4 帧 × 40 B，50 帧/秒；**音频是明文 Opus**（TOC 只有 `0x4b`/`0x48`），不用解密
- 卡同时在本地生成加密录音文件；解密后与实时流前 2950 帧逐帧一致，所以实时流断了也能从文件补齐
- 官方流程里补发的 `0x54` 落在音频开始之后，卡没回复；"两段式启动"和"发 `0x54` 后断开"都不成立（已配对状态下发 `0x54` 未复现断开，此前的断开原因未单独定位）
- 停止后普通录音（`0x51`）和列表（`0x90`）正常

**对设计的影响**：路径 C 用 `0x51 [1]` 启动；断线补传可直接用卡上的同名录音文件，不必 App 自己缓存全部音频。未覆盖：iOS 上的实时流、超过 60 s 的长时实时录音。证据：`evidence/v1-live/`（PR #16）；协议细节见 `docs/PROTOCOL.md` §4.3、§5.1。

#### H1 结论（2026-11-06，#5）

**H1 否定：配对不需要断开重连。** 解绑、重新配对各 3 轮，每轮在同一连接内用 `0xA1` 查询，结果都已反映 `0xA0` 的写入，断开重连后也一致（3/3 解绑、3/3 配对）。

- `0xA0`（绑定、解绑）回 1 字节 `0x01` 确认；解绑后 `0xA1` 返回 `isBonded=0`，不带 bondId
- 卡已绑定别的 bondId 时，`pair` 会被拒；用已存的 bondId 重复 `pair` 是空操作
- 重新配对后下载的录音与备份逐字节一致，解密不受影响

**对设计的影响**：§4.3 配对流程去掉"断开重连"一步，改为 `0xA1` 查询确认。先前"同一连接内不生效"的观察是误判。证据：`evidence/v3-pair/`（PR #17）。

#### H5 结论（2026-11-06，#5）

**按键录音成立。** 卡上按键录的 15,180,060 B 文件（Opus 48 kHz 单声道，7590 s）能被 `0x90` 列出、下载、解密、完整解码，音量正常（前 600 s 平均 −24.2 dB）。

**约束：录音进行中 `0x90` 返回空列表**（`0x56` 显示 rec=1），停止后全部文件才重新出现。所以 App 不能把"列表为空"当成"卡上没录音"，同步前要先查 `0x56` 的录音状态。

同一文件也测出蓝牙吞吐基线：3 次 23.69 / 23.51 / 23.60 KB/s，均值 **23.60 KB/s**（±0.4%），3 次解码结果一致。这个基线供 V2 定通过线（见 V2 结论）。证据：`evidence/v3-pair/`（PR #17）。

#### H6 结论（2026-11-06，#7 + #21）

| 项 | 结果 |
|---|---|
| 连卡热点 | **成立**。批准过系统弹框后 13/14（93%，含最多 3 次重试）；第一次尝试即成功 11/14（79%） |
| 后台蓝牙 | **成立**。保持连接时前台、后台、锁屏各 ≥ 3 次均在约 1.5 s 内发现新录音 |
| 后台扫描发现设备 | **不可行**。卡的广播不含服务 UUID，iOS 后台扫描必须带服务过滤 |

**硬约束：首次加入热点必须有一次人工批准。** `NEHotspotConfiguration` 对未批准过的 SSID 会弹系统确认框，不点就挂到超时并回落到原网络 —— V7 那轮 2/14 的失败全部由此产生（#21 第 1 轮等了 362.6 s）。批准后 iOS 记住该 SSID，换新密码、每轮 `removeConfiguration` 都不再弹框。

**对设计的要求**：快传首次使用要设计成明确的引导步骤（"即将连接录音卡热点，请点允许"），不能静默重试。自动同步依赖"保持连接"而非后台扫描，所以连接丢失后的恢复路径（`connectWhenSeen` 式的挂起连接）是必需项，不是优化项。

残留 1/14 的失败原因未定位（当轮定位权限被拒，`NEHotspotNetwork.fetchCurrent()` 读不到 SSID，无法区分"没切网"与"切了网但路由不通"）。证据：`evidence/v21-hotspot/`。

#### H4 结论（2026-11-06，#19）

原假设的**路径**被否定：TCP 协议**没能**从官方 JS 里逆出来。但换了来源后拿到了更直接的东西 —— App 内置固件（zlib 压缩的 Rockchip `RKFP` 镜像）里的 `recpen_file_server` 暴露了完整命令集：

- 明文命令 `list_files`、~~`pull` / `pull_file`、`send_file`~~、`delete`，未知命令回 `unknown %s,len=%d`
  —— **更正（2026-11-06，#6）**：下载命令是 `get`（固件日志 `send_file`），`pull` 是上传到卡
- ~~列表项 `{"name","size","recd","rec","upload"}`，分片 `{"name","size","index","end"}`~~
  —— **更正**：快传回包是二进制帧，不是 JSON；这两个 JSON 模板属于固件别的模块
- 录音目录 `/sdcard/record`，扩展名 `.opus`，端口 6718，地址 `192.168.88.1`

**所以 §7.3 的"H4 不成立"回退不必触发。** V2（#6）从"协议未知、要靠抓包猜"转为"按已知命令集逐条验证"；命令的确切分隔符、参数格式、大小写仍需真机实测。详见 `docs/craft-anything-evaluation.md` §5.1。

#### V2 结论（2026-11-06，#6）

**快传成立，远超通过线。** 在 iPhone 12 上用固件命令集实测（线格式见 `docs/PROTOCOL.md` §7）：

| 项 | 结果 | 通过线 |
|---|---|---|
| 一致性 | 15,180,060 B 录音 3 次快传，原始字节与 iPhone 蓝牙下载相同；Mac 解密后 ogg 与 #5 相同 | SHA-256 与蓝牙一致 |
| 吞吐 | 均值 **777.75 KB/s**（741.71–799.21，3 次）；#5 蓝牙基线 23.60 KB/s 的 **33 倍**，同一 iPhone 蓝牙（25.55 KB/s，1 次）的 30 倍 | ≥ 2 倍 |

**对设计的影响**：

- 长录音同步走快传，蓝牙只做控制和小文件。两小时录音（15 MB）从约 10 分钟降到约 19 s 传输
- 端到端耗时的大头是**加入热点**（实测 45–80 s），不是传输。小于约 1.5 MB 的文件走蓝牙更快，切换阈值留给 #13 定
- 首次加入要人工批准一次（见 H6），所以快传的首次使用要有引导步骤

**未覆盖**：卡满电不充电时的吞吐（本次 9–12% 电量且在充电）；后台、锁屏下的快传；`pull`、`delete`、`quit` 三个命令。证据：`evidence/v2-fasttransfer/`（PR #23）。

**目前无解的一项**：如果实时录音或 WiFi 快传使用了无法从官方 App 推断的私有协议，对应功能可能在不改固件的前提下无法实现。~~在 V1、V2 完成前无法排除。~~ 对 WiFi 快传已可排除（见 H4 结论：命令集来自固件，不依赖官方 App 的可推断性）；对实时录音也已排除（见 H2 结论：`0x51 [1]` + 明文 `0x68`）。

## 8. 结论与下一步

### 8.1 建议

做一个"设备功能离线优先"的 App 加多用户后端：设备通道、本地录音库、播放与导出在 App 内闭环；账号、存储、转写、AI、实时转写、云同步在后端。配对本地完成，绑定码登录后备份；OTA 默认不做；加密沿用派生密钥；ASR 和大模型都可替换。
