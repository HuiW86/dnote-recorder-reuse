# beanpod（豆仓）评估：哪些可以借鉴，哪些不采纳

- 分析对象：[andyhuo520/beanpod](https://github.com/andyhuo520/beanpod)，提交 `0d00fab`（2026-11-16，版本 0.1.0），MIT 许可（Copyright (c) 2026 berryxia）
- 方法：克隆后通读源码（约 1.08 万行 Swift，另有 Python 脚本），逐项对照 `features.md` 的里程碑。**没有编译和运行它**，下文对它行为的描述都来自源码和 README
- 来源：#65
- 日期：2026-11-16

本文只记录结论和代码位置，不复制它的源码。

---

## 1. 结论先行

| 问题 | 结论 |
|---|---|
| 能直接拿来用吗 | **设备层不能**。它支持的是 Anker 录音豆（D3200）和得到录音卡（GSC10），帧格式、命令、加密、Wi‑Fi 快传都和我们的卡不同 |
| 值得借鉴吗 | **值得，集中在上层**：转写、纪要整理的提示词与数据结构、录音库的回收站。这些正好是我们还没开工的 M2 和 M4 |
| 最大的收获 | ① 它证明了「本机转写」这条路在同类 App 里走得通，与我们的离线优先原则一致（#67）；② 一套现成的中文纪要提示词，可以直接当 #12 评估的候选（#68）；③ 对照它的解码代码，发现我们入库前不校验音频帧，换固件时有丢录音的风险（#66） |
| 代码能整段搬吗 | **少数能，多数不能**。它的上层是一个 1200 行的 `BeanStore` 加 JSON 文件存储，默认全部跑在主线程隔离下，只有协议库有测试（22 个）。我们是分模块的 Swift Package 加 GRDB，M1 模块有两百多个测试。搬的是提示词、数据结构和做法，调用代码按我们的分层重写 |
| 成熟度 | 0.1.0，评估当天才发第一个安装包；得到录音卡的支持自述「还没在实机上测过」；iPhone 版自述「试验阶段」。当参考，不当依赖 |

## 2. 它是什么

原生 macOS App（另有试验中的 iPhone 版），没有自己的服务器：

| 层 | 内容 | 规模 |
|---|---|---|
| `Sources/BeanKit/` | 两种设备的帧、命令、解密，Ogg 封装，Opus 解码 | 约 1000 行，有测试 |
| `Shared/` | 蓝牙、录音库、转写与整理流程、知识库，Mac 和 iPhone 共用 | 约 6000 行，无测试 |
| `App/`、`Mobile/` | 界面 | — |
| `Sources/beanpod/` | 命令行工具与 MCP 服务 | 406 行 |

转写有三档：本机模型（Qwen3‑ASR，经 llama.cpp，仅 Mac）、系统语音识别（Mac 和 iPhone）、用户自己填密钥的云端服务。纪要整理用本机模型或用户自己填密钥的大模型。

## 3. 与我们的差异

| | beanpod | 本项目 |
|---|---|---|
| 设备 | Anker 录音豆、得到录音卡 | D·NOTE 录音卡 |
| 平台 | macOS 为主，iPhone 试验 | iOS |
| 后端 | 没有；用户自己填服务商密钥，App 直连 | 自建后端统一管密钥（ADR-002、ADR-003），App 不持有密钥（#12） |
| 账号 | 没有 | M2 起有，放在 AI 功能之前 |
| 本地存储 | JSON 文件 | GRDB（ADR-007） |
| 设备功能离线 | 是 | 是（硬规则 3） |
| 协议结论的证据 | 文档里逐条标来源：实测、安装包核对、未独立核实 | `evidence/` 目录，要求可复现（硬规则 6） |

两个项目的出发点相同：让用户不依赖厂商的 App 和云，用上自己设备里的录音。分歧在 AI 能力放哪里：它交给用户自己配置，我们交给后端。我们的用户是手里有卡、官方 App 失效的普通用户，让他们去各家开放平台注册并填密钥不现实，所以这个分歧不改。

## 4. 采纳的项

### 4.1 入库前校验 Opus 帧头 → #66（建议在 TestFlight 外部测试前完成）

对照它的解码代码时发现的，是我们自己的缺口。

- 我们按「固定 40 字节一帧、每帧 20 ms」切帧并封装（`OggOpus.splitFrames`，`SyncEngine.swift` 的 `ConvertedAudio`），不检查内容；解密只校验文件头，未加密的文件完全没有校验
- 这些参数只在固件 v1.50 的一张卡上验证过（硬规则 7）。换一个帧长不同的固件，会得到播不了的 OGG，但它仍会被记为已存入；开了「同步后删除」时，卡上的唯一副本随后被删
- beanpod 支持第二种设备时遇到过 20 ms 和 60 ms 两种帧长，做法是读每个包第一个字节（TOC，RFC 6716 §3.1）算帧长：`Sources/BeanKit/GetSeed.swift` 的 `samplesPerPacket`，测试样本 `card20ms.ogg`、`card60ms.ogg`
- 我们要做的比它多一步：帧头不符合预期时不入库、不删卡上文件

### 4.2 本机转写作为离线一档 → #67（先测量，再决定是否加入范围）

- `Shared/Transcriber.swift`（50 行）：`SFSpeechRecognizer` 加 `requiresOnDeviceRecognition = true`，录音不出设备。它的 iPhone 版在没有配置云端转写时走这条路
- 与我们的关系：`competitor-analysis.md` §2 第 2 条记过，竞品里只有讯飞 SR702 能本机转写。如果在真卡录音上质量可用，「不登录也能出文字稿」是离线优先原则的自然延伸，后端不可用时也有兜底（`backend-design.md` §7.1 第 5 条）
- 已知限制：不区分说话人，不能替代 F1；它的实现把整段录音当成一句话返回，没有分句时间戳；中文长录音在 iPhone 上的实际表现**未知**，这正是 #67 要测的
- 这是范围变化（`features.md` 目前没有这一项），所以 #67 只测量并给结论，值得做再另开 issue 改范围、写 ADR

### 4.3 后端转写模块用 OpenAI 兼容接口做统一适配 → #67

- `Shared/CloudASR.swift`（224 行）用同一个客户端接了硅基流动（SenseVoiceSmall）、小米 MiMo、OpenAI、Groq
- 可借鉴的细节：长录音沿静音处切成不超过 5 分钟的段再上传，不把一句话切在两段中间；服务商不返回时间戳时按标点分句、按字数估时间；服务商不认压缩格式或带时间戳的返回时，退回最朴素的请求
- 我们把这个适配器放在后端（Python），不放在 App 里

### 4.4 纪要提示词与数据结构 → #68

- `Shared/Domain.swift` 的 `Scene`：10 种场景，每种有一句定义、一组栏目、一组关键词
- `Shared/Analyzer.swift`：整理、分段压缩、润色、改写、问答五类提示词，输出结构是标题、摘要、分栏要点、待办、标签、人物
- 对应 G1、G2a、G3。#12 的前置任务要比较 3 套提示词，这是现成的一套
- 缺口：官方 App 的大纲、思维导图、金句（G1），这套提示词没有，要另外补

### 4.5 进入对应里程碑时参考（现在不开 issue）

| 项 | beanpod 位置 | 我们的条目 | 可借鉴的做法 |
|---|---|---|---|
| 最近删除 | `Shared/Trash.swift` | D1b（M4） | 本机删除先保留 7 天，文字稿和纪要一起保留，可原样恢复，到期自动清除，删完当场可撤销；**从设备上删除不经过回收站**，照旧先确认。我们用 GRDB 实现时，给 `recording` 加删除时间字段即可，不用它的「挪文件夹加 JSON」 |
| 导出 Markdown | `Shared/Pipeline.swift` `markdown(_:)` | J1（M4） | 文件头带日期、场景、时长、标签、人物（YAML frontmatter），正文依次是摘要、分栏要点、待办（复选框）、带时间的文字稿，可直接放进 Obsidian |
| 显示模型输出的 Markdown | `Shared/Markdown.swift` | G1、G3 的界面 | 模型写的加粗经常不合规范（星号里带空格、星号后紧跟文字），系统解析器会原样吐出星号；它自己配对 `**` |
| 处理进度与预计时间 | `Shared/ProcessingETA.swift` | F1、G1 的任务状态 | 按实际耗时做指数平均，估算每条还要多久、整批几点做完 |
| 纠错词库 | `Shared/Pipeline.swift` `applyVocabulary` | F1 | 用户在文字稿里改过的词，以后转写自动替换 |
| 上次在设备里的录音不见了 | `Shared/BeanStore.swift` `reportConnected` | C1 | 连上时对比上次的文件清单，少了又不是本 App 删的就提示。我们的卡目前只有本 App 会删文件，价值不大；将来同一张卡配多台手机时再看 |
| 截图脚本 | `Mobile/shots.sh` | 上架截图 | 用启动参数直接打开指定页面，`simctl` 逐页截图 |
| 示例数据模式 | `scripts/make-demo-library.py`、启动参数 `-demo` | Beta 审核、截图 | 虚构的录音库，不连蓝牙。Beta 审核目前的方案是演示视频（PR #64 的 `docs/release/testflight.md` §3.4）；如果审核因为没有硬件被拒，再考虑做 |
| 协议文档逐条标来源 | `docs/PROTOCOL.md` | `docs/PROTOCOL.md` | 每条标「实测」「安装包核对」「未独立核实」。我们的证据在 `evidence/`，但 `PROTOCOL.md` 的表格没有逐条指向证据；下次修订时加一列 |
| 致谢与免责声明 | `README.md`、`NOTICE` | 公开的隐私政策页、将来公开仓库时 | 写明非官方、与厂商无关、商标归属、侵权联系方式 |

## 5. 不采纳的项

| 项 | 理由 |
|---|---|
| 设备协议、解密、Wi‑Fi 快传的代码 | 设备不同。它的快传是 WebSocket 加 UDP 保活，我们的是 TCP 文本命令加二进制帧（`PROTOCOL.md` §7） |
| 用户自己填密钥、App 直连服务商 | 与 #12 的验收标准「App 不持有任何 ASR 或大模型的 API Key」冲突，目标用户也配不了（§3） |
| 录完当场问「留着还是不要」，不要就直接从设备删除 | 与硬规则 2 冲突：卡上的文件要先存入手机才能删 |
| JSON 文件存储、单个大的状态对象 | 我们已定 GRDB 和分模块（ADR-007、`prd.md` §1） |
| 本机大模型（llama.cpp 跑 Qwen3）| 只能在 Mac 上跑，它自己的 iPhone 版也是空实现（`Mobile/Stubs.swift`） |
| Opus 解码器 | 我们已有同样用系统解码器的实现（`Player/OggOpusDecoder.swift`），并且处理了它没处理的 pre-skip |
| MCP 服务与命令行、飞书妙记同步、链接导入、做成视频、语音输入、英语学习模式、吉祥物 | 不在 `features.md` 范围内，多数只适用于 Mac |
| 「职业」设定 | G2a 的模板已承担同样的作用（#68） |
| 多语言界面 | O1a 已定界面先只做简体中文；将来做时可参考它的 String Catalog 加同步脚本（`scripts/i18n-sync.py`） |
