# beanpod（豆仓）评估：哪些可以借鉴，哪些不采纳

- 分析对象：[andyhuo520/beanpod](https://github.com/andyhuo520/beanpod)，提交 `0d00fab`（2026-11-16，版本 0.1.0），MIT 许可（Copyright (c) 2026 berryxia）
- 方法：克隆后通读源码（约 1.08 万行 Swift，另有 Python 脚本），逐项对照 `features.md` 的里程碑。**没有编译和运行它**，下文对它行为的描述都来自源码和 README
- 来源：#65
- 日期：2026-11-16（当天两次修订：补上 §4.6、§4.7，见 §8）

本文只记录结论和代码位置，不复制它的源码。

---

## 1. 结论先行

| 问题 | 结论 |
|---|---|
| 能直接拿来用吗 | **对 D·NOTE 卡不能**：它支持的是 Anker 录音豆（D3200）和得到录音卡（GSC10），协议不同。**但它的协议库可以整库复用**：以后闻笺接入这两种设备时，把 BeanKit 作为依赖引入，不用重写（§4.7，#73） |
| 值得借鉴吗 | **值得，集中在上层**：录音到了手机之后的体验、转写、纪要整理。它在这几处比我们的设计想得周到 |
| 我们的设计哪里没到位 | ① M1 只管「录音安全到手机」，到了之后很薄：删了找不回、不能改名、导出的文件别人打不开、没有文字（§4.6，#70）；② AI 能力只走自建后端，后端一停用户会第二次失去功能，这正是本项目要避免的事（ADR-009，#71） |
| 另外三个具体收获 | ① 本机转写在同类 App 里走得通（#67）；② 一套现成的中文纪要提示词，可以直接当 #12 评估的候选（#68）；③ 对照它的解码代码，发现我们入库前不校验音频帧，换固件时有丢录音的风险（#66） |
| 代码能整段搬吗 | **少数能，多数不能**。它的上层是一个 1200 行的 `BeanStore` 加 JSON 文件存储，默认全部跑在主线程隔离下，只有协议库有测试（22 个）。我们是分模块的 Swift Package 加 GRDB，M1 模块有两百多个测试。搬的是提示词、数据结构和做法，调用代码按我们的分层重写 |
| 成熟度 | 0.1.0，评估当天才发第一个安装包；得到录音卡的支持自述「还没在实机上测过」；iPhone 版自述「试验阶段」。当参考，不当依赖 |

## 2. 它是什么

原生 macOS App（另有试验中的 iPhone 版），没有自己的服务器：

| 层 | 内容 | 规模 |
|---|---|---|
| `Sources/BeanKit/` | 两种设备的帧、命令、解密，Ogg 封装，Opus 解码 | 约 1000 行，有测试 |
| `Shared/` | 蓝牙、录音库、转写与整理流程、知识库，Mac 和 iPhone 共用 | 约 6000 行，无测试 |
| `App/`、`Mobile/` | 界面 | — |
| `Sources/beanpod/` | 命令行工具与 MCP 服务 | 406 行 |

转写有三档：本机模型（Qwen3‑ASR，经 llama.cpp，仅 Mac）、系统语音识别（Mac 和 iPhone）、用户自己填密钥的云端服务。纪要整理用本机模型或用户自己填密钥的大模型。

## 3. 与我们的差异

| | beanpod | 本项目 |
|---|---|---|
| 设备 | Anker 录音豆、得到录音卡 | D·NOTE 录音卡 |
| 平台 | macOS 为主，iPhone 试验 | iOS |
| 后端 | 没有；用户自己填服务商密钥，App 直连 | 自建后端统一管密钥（ADR-002、ADR-003），App 不持有密钥（#12） |
| 账号 | 没有 | M2 起有，放在 AI 功能之前 |
| 本地存储 | JSON 文件 | GRDB（ADR-007） |
| 设备功能离线 | 是 | 是（硬规则 3） |
| 协议结论的证据 | 文档里逐条标来源：实测、安装包核对、未独立核实 | `evidence/` 目录，要求可复现（硬规则 6） |

两个项目的出发点相同：让用户不依赖厂商的 App 和云，用上自己设备里的录音。分歧在 AI 能力放哪里：它交给用户自己配置，我们交给后端。我们的用户是手里有卡、官方 App 失效的普通用户，让他们都去各家开放平台注册并填密钥不现实，所以后端这条路要保留。但它的做法有一点我们没有：没有哪一个服务停了会让 AI 功能整体失效。这一点按 ADR-009 吸收：用户自配服务与后端并列为两条主路径（§4.6 第 8 行、§4.7）。

## 4. 采纳的项

### 4.1 入库前校验 Opus 帧头 → #66（建议在 TestFlight 外部测试前完成）

对照它的解码代码时发现的，是我们自己的缺口。

- 我们按「固定 40 字节一帧、每帧 20 ms」切帧并封装（`OggOpus.splitFrames`，`SyncEngine.swift` 的 `ConvertedAudio`），不检查内容；解密只校验文件头，未加密的文件完全没有校验
- 这些参数只在固件 v1.50 的一张卡上验证过（硬规则 7）。换一个帧长不同的固件，会得到播不了的 OGG，但它仍会被记为已存入；开了「同步后删除」时，卡上的唯一副本随后被删
- beanpod 支持第二种设备时遇到过 20 ms 和 60 ms 两种帧长，做法是读每个包第一个字节（TOC，RFC 6716 §3.1）算帧长：`Sources/BeanKit/GetSeed.swift` 的 `samplesPerPacket`，测试样本 `card20ms.ogg`、`card60ms.ogg`
- 我们要做的比它多一步：帧头不符合预期时不入库、不删卡上文件

### 4.2 本机转写作为离线一档 → #67 测量，通过后在 M1.5 交付（X9）

- `Shared/Transcriber.swift`（50 行）：`SFSpeechRecognizer` 加 `requiresOnDeviceRecognition = true`，录音不出设备。它的 iPhone 版在没有配置云端转写时走这条路
- 与我们的关系：`competitor-analysis.md` §2 第 2 条记过，竞品里只有讯飞 SR702 能本机转写。如果在真卡录音上质量可用，「不登录也能出文字稿」是离线优先原则的自然延伸，后端不可用时也有兜底（`backend-design.md` §7.1 第 5 条）
- 已知限制：不区分说话人，不能替代 F1；它的实现把整段录音当成一句话返回，没有分句时间戳；中文长录音在 iPhone 上的实际表现**未知**，这正是 #67 要测的
- 已作为 X9 写进 `features.md`（M1.5，P1），前提是 #67 测出来质量可用；不可用就把 X9 改为 deprecated。分层的决定见 ADR-009

### 4.3 后端转写模块用 OpenAI 兼容接口做统一适配 → #67

- `Shared/CloudASR.swift`（224 行）用同一个客户端接了硅基流动（SenseVoiceSmall）、小米 MiMo、OpenAI、Groq
- 可借鉴的细节：长录音沿静音处切成不超过 5 分钟的段再上传，不把一句话切在两段中间；服务商不返回时间戳时按标点分句、按字数估时间；服务商不认压缩格式或带时间戳的返回时，退回最朴素的请求
- 我们把这个适配器放在后端（Python），不放在 App 里

### 4.4 纪要提示词与数据结构 → #68

- `Shared/Domain.swift` 的 `Scene`：10 种场景，每种有一句定义、一组栏目、一组关键词
- `Shared/Analyzer.swift`：整理、分段压缩、润色、改写、问答五类提示词，输出结构是标题、摘要、分栏要点、待办、标签、人物
- 对应 G1、G2a、G3。#12 的前置任务要比较 3 套提示词，这是现成的一套
- 缺口：官方 App 的大纲、思维导图、金句（G1），这套提示词没有，要另外补

### 4.5 进入对应里程碑时参考（现在不开 issue）

| 项 | beanpod 位置 | 我们的条目 | 可借鉴的做法 |
|---|---|---|---|
| 导出 Markdown | `Shared/Pipeline.swift` `markdown(_:)` | J1（M4） | 文件头带日期、场景、时长、标签、人物（YAML frontmatter），正文依次是摘要、分栏要点、待办（复选框）、带时间的文字稿，可直接放进 Obsidian |
| 显示模型输出的 Markdown | `Shared/Markdown.swift` | G1、G3 的界面 | 模型写的加粗经常不合规范（星号里带空格、星号后紧跟文字），系统解析器会原样吐出星号；它自己配对 `**` |
| 处理进度与预计时间 | `Shared/ProcessingETA.swift` | F1、G1 的任务状态 | 按实际耗时做指数平均，估算每条还要多久、整批几点做完 |
| 纠错词库 | `Shared/Pipeline.swift` `applyVocabulary` | F1 | 用户在文字稿里改过的词，以后转写自动替换 |
| 上次在设备里的录音不见了 | `Shared/BeanStore.swift` `reportConnected` | C1 | 连上时对比上次的文件清单，少了又不是本 App 删的就提示。我们的卡目前只有本 App 会删文件，价值不大；将来同一张卡配多台手机时再看 |
| 截图脚本 | `Mobile/shots.sh` | 上架截图 | 用启动参数直接打开指定页面，`simctl` 逐页截图 |
| 示例数据模式 | `scripts/make-demo-library.py`、启动参数 `-demo` | Beta 审核、截图 | 虚构的录音库，不连蓝牙。Beta 审核目前的方案是演示视频（PR #64 的 `docs/release/testflight.md` §3.4）；如果审核因为没有硬件被拒，再考虑做 |
| 协议文档逐条标来源 | `docs/PROTOCOL.md` | `docs/PROTOCOL.md` | 每条标「实测」「安装包核对」「未独立核实」。我们的证据在 `evidence/`，但 `PROTOCOL.md` 的表格没有逐条指向证据；下次修订时加一列 |
| 致谢与免责声明 | `README.md`、`NOTICE` | 公开的隐私政策页、将来公开仓库时 | 写明非官方、与厂商无关、商标归属、侵权联系方式 |

### 4.6 产品设计：我们没想到位的地方 → #70（M1.5）、#71

M1 的页面规格是「先模仿官方，再改进」（`product-spec.md` 开头），而官方 App 的这些功能都靠云端。结果是 M1 把设备这一半做扎实了，录音到了手机之后的体验却停在最小形态，剩下的全部排在 M2 以后、等后端。beanpod 没有后端，所以它把不需要后端的事都先做了。逐项对照：

| # | 方面 | beanpod 怎么做 | 我们现在 | 吸收方式 | 落到 |
|---|---|---|---|---|---|
| 1 | 删除 | 本机删除先进「最近删除」放 7 天，文字稿和纪要一起留着，可原样恢复；删完顶上有「撤销」；到期自动清除（`Shared/Trash.swift`） | 确认后直接删，不可逆（`product-spec.md` §4.5 列为 L3）。卡上那份已删时，录音彻底没了。回收站排在 M4 P2 | 提前到 M1.5。用 GRDB 给录音加删除时间字段，不用它的「挪文件夹加 JSON」 | D1b |
| 2 | 导出 | 导出 M4A、WAV | 只导出 OGG，理由是「OGG 已可播放和分享」。这个理由不成立：我们自己的播放器注释写着只有 iOS 27 能直接打开 OGG Opus，更早的系统要先解码（`Player/OggOpusDecoder.swift`）。收到文件的人多半打不开 | 提前导出 M4A；OGG 保留为「原始文件」选项。微信里能否直接播放要真机验证 | E1b |
| 3 | 标题 | 可重命名；AI 起标题，可让它换一个角度重起；手改过的标题重新整理时不覆盖 | 标题固定为开始时间，不能改 | M1.5 加重命名；M2 的 G1 加 AI 标题，沿用「手改的不覆盖」 | X6、G1 |
| 4 | 文字稿 | 没有配置任何服务时，用系统语音识别在本机出文字（`Shared/Transcriber.swift`） | 不登录没有任何文字；后端上线前卡只是录音机 | 见 §4.2 | X9 |
| 5 | 录音中 | 「标重点」按钮，回放时跳到标记处；全屏录音页只留时间、声波、三个按钮 | 只有时长和开始、暂停、停止 | App 端按已录时长记标记，不需要卡支持。全屏录音页也跟（`design-spec.md` §3，#74） | X7 |
| 6 | 同步的告知 | 连上时说一句：有几条新录音在同步，或都同步过了；不在前台时发系统通知 | 只有 App 内的同步卡片；`product-spec.md` §6 写明不做本地通知。我们支持后台同步，用户却不知道同步完没有 | 后台同步完成时发本地通知 | X8 |
| 7 | 不想要的录音 | 录完浮出一张卡片问「留着还是不要」，10 秒不理默认留着，选了不要还有 5 秒可反悔（`Shared/KeepOrDiscard.swift`） | 要等同步完，再去列表里删；卡上还留一份 | 需求是真的，做法要改：它是不下载、直接从设备删，与硬规则 2 冲突。我们仍先存入手机，再把本机这条移入最近删除、删卡上文件。用户看到的效果一样 | X10 |
| 8 | AI 的耐久性 | 三档：本机识别、本机模型、用户自配的服务。没有单点 | 转写、总结、对话全部只走自建后端。后端由一个人维护，停了用户会第二次失去功能 | 分三档：本机转写为底、后端为主、用户自配服务为后备。第三档与 #12 的一条验收标准有出入，由 ADR-009 决定 | X9、X11、#71 |
| 9 | 选模板 | 自动判断场景（会议、访谈、电话等 10 种），每种场景有自己的栏目；可以手动改 | 计划是用户从内置模板里选 | 默认自动判断，用户可以改 | G2a、#68 |
| 10 | 纪要的内容 | 标题、摘要、分栏要点、**待办**、标签、人物；首页汇总所有录音里没完成的待办 | G1 列了总结、大纲、思维导图、金句、标签，没有待办 | G1 加待办。首页汇总待办放到 M2 页面规格里定 | G1 |
| 11 | 文字稿与音频 | 点一句从那里播放，正在读的那句高亮 | 未设计（F1 的页面规格还没写） | 写进 F1 | F1 |
| 12 | 没有设备时 | 用手机麦克风录、导入音频文件，照样转写整理 | 没有卡时只能看已同步的录音；导入在 M4（E2），手机录音不在范围内 | 暂不提前。我们的用户都有卡；M4 做 E2 时一并评估手机录音 | E2 |

第 1、2、3 行是我们的设计缺口，与 beanpod 无关也该补；它只是让缺口显出来。

### 4.7 做加法：自配服务、Mac 与创作功能、多设备 → #71、#72、#73

这三组在本文前两版里都判为不采纳，理由分别是「目标用户配不了」「和用卡录会议的用户对不上」「设备不同」。这些理由说的是今天的用户和今天的设备，拿来限制产品以后能长成什么样并不合适。用户 2026-11-16 决定三组都吸收。

| 组 | 吸收什么 | 怎么排 | 现实约束 |
|---|---|---|---|
| 用户自配 AI 服务（X11） | 填一个兼容 OpenAI 接口的地址和密钥，转写、总结、对话不经过我们的后端。与「账号加后端」并列为两条主路径，第一次用 AI 时让用户选（ADR-009） | M2 的 P0，**先于后端交付**。这条路不需要账号、后端、备案和短信通道，所以 AI 功能的上线时间不再被后端卡住 | 录音和文字稿会发到用户选的第三方，界面和隐私政策要写明；提示词只留一份来源 |
| Mac 版与创作功能（X12～X16、X19、X20） | Mac 版 App；链接导入；改写成口播稿、脚本、社媒帖；语音输入；做成视频；MCP 接入 AI 助手；逐句回听与英语学习模式 | 改写和学习模式是纯提示词功能，排 M4；其余排新里程碑 M5（#72） | `ReviveKit` 已声明支持 macOS 14，Mac 版要补的是界面层。语音输入和视频网站下载在 iPhone 上受系统限制，先在 Mac 做；iPhone 上的链接导入先做播客 |
| 多设备接入（X17） | Anker 录音豆、得到录音卡 | 新里程碑 M6（#73），时间取决于什么时候拿到设备 | 协议库 BeanKit 可以直接作为依赖（MIT，只依赖 Foundation 和 CryptoKit，与 `ReviveKit` 平台一致）。**必须有真机**：beanpod 自己都没在得到录音卡上测过。硬规则 2 对新设备照样生效；硬规则 5 的商标清单要扩（ADR-010） |

现在就该做的一件事：不要再加深代码对 D·NOTE 一种卡的直接依赖。M1.5 和 M3 新写的代码，按 ADR-010 里的设备接口边界来写。

## 5. 不采纳或暂不排期的项

| 项 | 理由 |
|---|---|
| JSON 文件存储、单个大的状态对象 | 我们已定 GRDB 和分模块（ADR-007、`prd.md` §1） |
| 本机大模型（llama.cpp 跑 Qwen3）| 不是不做：只能在 Mac 上跑，随 M5 的 Mac 版评估（#72） |
| Opus 解码器 | 我们已有同样用系统解码器的实现（`Player/OggOpusDecoder.swift`），并且处理了它没处理的 pre-skip |
| 用 beanpod 的协议代码驱动 D·NOTE 卡 | 协议不同，做不到。它的协议库用于它支持的那两种设备（§4.7） |
| 飞书妙记同步 | 只对 Anker 录音豆有意义（它的官方 App 把录音同步进飞书），随 M6 接入该设备时再评估 |
| 「职业」设定、多语言界面 | 不是不做，是现在没有排期：进入 M2 页面规格和上架前各看一次 |
| 吉祥物、它的图标和强调色 | 那是它的品牌。界面的其余部分参照它来做，强调色用闻笺图标自己的红（`design-spec.md`，#74） |
