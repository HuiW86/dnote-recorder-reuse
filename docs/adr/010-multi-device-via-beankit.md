# ADR-010：接入其他录音设备时复用 BeanKit

**日期**　2026-11-16
**状态**　Proposed
**来源**　#73；评估依据 `docs/beanpod-evaluation.md` §4.7（#65）

## 背景

- 用户 2026-11-16 决定：闻笺后面可以接入 D·NOTE 以外的设备。方向已定，本 ADR 只决定技术做法，进入 M6 时定稿。
- beanpod 已经实现 Anker 录音豆（D3200）和得到录音卡（GSC10）的协议。它的协议库 BeanKit 是独立的 Swift Package 库产品：MIT 许可，有 `v0.1.0` 标签，平台声明与 `ReviveKit` 相同（iOS 17、macOS 14），只依赖 Foundation 和 CryptoKit，不含蓝牙和联网代码，22 个测试。
- BeanKit 暴露的写命令里，不可逆的目前只看到「删除文件」，没有格式化和固件升级。
- 我们的设备层（`CardProtocol`、`CardLink`、`CardService`）是按 D·NOTE 一种卡写的，`SyncEngine` 直接依赖 `CardService`。
- 约束：硬规则 2（先存入再删）、硬规则 6（真机证据）对任何设备都生效；我们目前没有这两种设备。beanpod 自述得到录音卡「还没在实机上测过」，录音豆只在固件 04.92 上测过。

## 候选方案

**A. 把 BeanKit 作为 Swift Package 依赖，固定到提交号**
- 优点：不重写协议；上游修了问题可以跟进；我们只写连接层和到 `SyncEngine` 的适配。
- 缺点：上游才 0.1.0，接口可能变；库里有我们用不到的内容（链接解析等）；出了协议问题要等上游或自己打补丁。

**B. 分叉 BeanKit 到自己名下再依赖**
- 优点：同 A，并且能自己改、自己发版；可以删掉用不到的部分，加上我们的禁止命令检查。
- 缺点：要自己跟上游合并。

**C. 参照它的协议文档，在 `ReviveKit` 里重写**
- 优点：风格和测试方式与现有模块一致，没有外部依赖。
- 缺点：重复造轮子，协议细节要重新踩一遍。

## 决定

建议 **A 起步，需要改动时转 B**。不选 C。

无论哪个方案，先做一件现在就能做、不依赖新设备的事：在 `CardService` 之上抽出与设备无关的接口（扫描、连接、设备信息、列表、下载、删除、可选的录音控制），`SyncEngine` 改为依赖这个接口，D·NOTE 的现有实现作为第一个实现。M1.5 和 M3 新写的代码按这个边界写，不再加深对 D·NOTE 的直接依赖。

## 后果

- 正面：新设备的协议层不用写；录音库、同步状态机、转写与整理对所有设备共用。
- 负面：多一个外部依赖；每种设备都要真机、证据目录和固件版本表；静态检查的禁止命令清单要按设备维护。
- 硬规则 5 要改写：Anker、soundcore、得到 同样不进 App 名称、图标、Bundle ID；描述里的「适用于 D·NOTE 录音卡」改为列出所支持的设备。M6 的第一个 PR 同步修改 `CLAUDE.md`。
- 要加 `NOTICE`：BeanKit 的 MIT 声明，以及它引用的两个上游协议项目的声明。
- 反悔成本：低到中。设备抽象本身对 D·NOTE 也有用（测试里的模拟卡已经是第二个实现）；依赖可以随时换成分叉或重写。
