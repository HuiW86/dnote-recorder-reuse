# ADR-007：App 本地数据库用 GRDB（SQLite）

**日期**　2026-11-06
**状态**　Accepted
**来源**　#36（父 issue #11）

## 背景

- M1 的本地录音库是录音的落点；卡上文件只有在「已存入」后才能删除（`prd.md` §4.2）。「已存入」要求 Recording 记录和 SyncItem 状态在**同一个数据库事务**里提交。
- 数据模型要随里程碑增长（M2 预留远端 id，M4 加文件夹、笔记、同步版本），每次发版都要能从旧版本平滑升级（`test-spec.md` T-M1-56）。
- 同步引擎的大部分测试在模拟卡上跑（`test-spec.md` §2），数据库要能在单元测试里快速创建和丢弃。
- 用户已同意按推荐选 GRDB（2026-11-06）。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **GRDB.swift**（SQLite 封装，v7.12.0） | 事务边界显式（`write { }` 内即一个事务）；版本化迁移（`DatabaseMigrator`）只追加不修改；内存数据库方便测试；支持观察查询结果驱动 SwiftUI；直接写 SQL，表结构就是 `prd.md` §5 的样子 | 第三方依赖；要自己写记录类型和查询 |
| SwiftData | 系统自带，写法最省事，和 SwiftUI 集成紧 | 事务边界和保存时机由框架控制，不透明；轻量迁移之外的迁移写起来麻烦；iOS 17 上的已知问题较多 |
| Core Data | 系统自带，成熟 | 模型和迁移要用编辑器维护，代码审查难；并发模型复杂 |

## 决定

App 本地数据库用 GRDB（SQLite），通过 Swift Package 依赖 `from: "7.12.0"`。表结构用版本化迁移维护，已发布的迁移不再修改。

## 后果

- 正面：同步引擎的事务语义可以直接写成代码并测试；迁移可审查。
- 负面：多一个第三方依赖，升级要跟进它的发布；记录类型与查询要手写。
- 反悔成本：中等。数据库是 SQLite 文件，换成其他 SQLite 封装只需改 Library 模块；换 SwiftData 或 Core Data 需要写一次数据迁移。Library 之外的模块不直接接触 GRDB，所以影响限于一个模块。
