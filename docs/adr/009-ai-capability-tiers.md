# ADR-009：AI 能力分三档，不只依赖自建后端

**日期**　2026-11-16
**状态**　Proposed
**来源**　#71；评估依据 `docs/beanpod-evaluation.md` §4.6 第 8 行（#65）

## 背景

- 本项目存在的原因是官方后台停了、整张卡不能用。M1 用「设备功能离线优先」解决了设备这一半（硬规则 3）。
- M2 起的转写、总结、对话全部只走自建后端（`backend-design.md` §4.4，ADR-002、ADR-003）。后端由一个人维护；它停了，用户会第二次失去 AI 功能。`competitor-analysis.md` §4 第 8 条把「停服预案」记为后期事项，没有落到设计里。
- beanpod 没有后端，AI 能力有三条互相独立的路：系统语音识别、本机模型、用户自己配置的服务。任何一家服务停了都不会整体失效。
- 约束：目标用户是普通用户，不能要求他们去开放平台注册、填密钥才能用（`beanpod-evaluation.md` §3）；App 里不能放我们自己的服务商密钥（#12 验收标准的本意）。

## 候选方案

**A. 维持现状：只走自建后端**
- 优点：一套代码路径；提示词、模型、用量都在服务端管；用户零配置。
- 缺点：后端是单点。不登录没有任何文字；后端停止服务后 AI 功能全部失效。

**B. 两档：本机转写为底，自建后端为主**
- 优点：不登录、不联网也有文字稿；后端不可用时还能出文字。不需要用户配置任何东西。
- 缺点：本机识别不区分说话人，中文长录音的质量未知（#67 要测）；后端停了之后，总结和对话仍然没有。

**C. 三档：B 加上「用户自配服务」作为后备**
- 在设置的高级选项里，可以填一个兼容 OpenAI 接口的地址和密钥（密钥存 Keychain）。填了之后，转写和总结可以不经过我们的后端。默认不出现在主流程里。
- 优点：后端停止服务后，愿意动手的用户仍能用上全部 AI 功能；也给不想把录音交给我们后端的用户一个选择。
- 缺点：多一套 App 直连的代码路径和测试；提示词要随 App 内置一份（或由后端下发后缓存）；用户填错地址和密钥带来的支持成本；审核时要说明这是用户自己的服务。

## 决定

建议采用 **C，分步做**：第一档（本机转写）在 M1.5 交付，前提是 #67 测量通过；第二档按 M2 原计划；第三档暂缓，最迟在 M4 结束前决定做不做，后端的接口和提示词存放方式现在就按「能被第三档复用」来设计。

#12 的验收标准「App 不持有任何 ASR 或大模型的 API Key」拟改写为「App 不内置任何由我们持有的服务商密钥；用户自己填的密钥只存在 Keychain」。

待用户确认后改为 Accepted。

## 后果

- 正面：AI 功能不再有单点；「不登录也能用」从设备功能延伸到文字稿；与离线优先原则一致。
- 负面：第一档要申请语音识别权限，隐私政策和权限说明要改；第三档若做，测试矩阵变大。
- 反悔成本：第一档低（纯本地功能，可以整体关掉）。第三档中等：做了之后再去掉，会影响已经在用的用户。
- 对其他文档的影响：`features.md` X9、X11；`backend-design.md` 要补停服预案一节；`prd.md` §7 的转写与总结接口保持与 OpenAI 兼容接口相近的输入输出，便于第三档复用（#67）。
