# ADR-006：证据数据脱敏与 `DEVICE_KEY_SECRET` 的去留

**日期**　2026-11-06
**状态**　Accepted
**来源**　#26；PR #16 审查意见（记录在 #10）

## 背景

- `evidence/` 下的日志和 README 含测试卡的序列号 `sn`、蓝牙地址 `btaddr`，部分日志含绑定码 `bondId`。
- `client/dnote_protocol.py` 里有 `DEVICE_KEY_SECRET`；音频密钥 = `HMAC-SHA256(DEVICE_KEY_SECRET, sn)`。两者同在仓库，拿到仓库就能算出这张卡的音频密钥。
- 当前仓库是私有的，卡归本人，风险低。
- `DEVICE_KEY_SECRET` 本身无法真正保密：它硬编码在官方 App 和固件里，我们的 App 解密时也必须带着它（`backend-design.md` §4.9）。真正要保护的是**某张卡的 `sn` 与这个常量的组合**。
- `docs/HANDOFF.md` §7 原先按「仅自用」定边界；现在产品定位是多用户分发，边界变了。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **新证据脱敏，旧证据在公开前统一清理** | 不打断现有工作；公开前有明确清单 | 私有期间仓库里仍有一张卡的完整信息 |
| 立刻改写全部历史 | 一次干净 | 要强推改写历史，所有 PR 链接和提交号失效，私有阶段收益小 |
| 把 `DEVICE_KEY_SECRET` 移出仓库 | 仓库单独泄露时算不出密钥 | App 和服务端仍要内置它，只是换了位置，保护效果有限 |

## 决定

1. **新证据**：`sn` 只记 SHA-256 的前 8 位十六进制；`btaddr` 只保留后两段；`bondId` 不记录。日志里需要原值的，写到 `.gitignore` 覆盖的本地文件。
2. **旧证据**：私有期间保持原样。
3. **仓库公开前必做**：清理旧证据里的 `sn`、`btaddr`、`bondId` 并改写历史；重新评估 `DEVICE_KEY_SECRET` 是否留在公开仓库；按多用户分发的定位重写 `HANDOFF.md` §7「法律与边界」。
4. `DEVICE_KEY_SECRET` 私有期间留在代码里。

## 后果

- 正面：规则简单，写进 `CLAUDE.md` 后每次生成证据都能照做。
- 负面：公开前有一次改写历史的工作量。
- 反悔成本：低。规则只影响新证据；收紧时把清理提前做即可。
