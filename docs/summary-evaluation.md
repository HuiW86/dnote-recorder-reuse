# 纪要提示词与模型评估（方法与评分表；数据待测）

**用途**　#12 的前置任务「大模型总结」：≥ 2 个模型 × 3 套提示词，在 5 分钟和 30 分钟样本上按统一评分表打分，选出默认方案。#68 要求 beanpod 的「场景—栏目」提示词作为其中一套。
**状态**　2026-11-21：方法、评分表、生成和汇总工具已就绪（`client/summary_generate.py`、`client/summary_scores.py`，都有测试，client-ci 会跑）。下面的数据都是 **待测**。
**上游**　#12、#68、ADR-009；`features.md` G1、G2a
**相关**　转写的评估见 `asr-evaluation.md`；两个评估用同一套录音

  - 用户填了职业时加的一段（G1 职业设定，#102）：#68 原来写「不采纳」，用户 2026-11-20 改为要做，文字是本项目另写的。这一段要求职业只影响顺序和说法，每一条都要在文字稿里找得到原话，不写「没有异议」这类推断（v105 真机发现模型会补，T-M2-07）。

## 2. 候选

### 2.1 提示词

| 代号 | 内容 | 来源 |
|---|---|---|
| A | App 当前的提示词（自动判断场景，含大纲、金句），职业留空 | `Summarizer.swift` |

### 2.2 模型

至少两个，从 App 里列出的服务商中选（`ServiceConfig.chat`）。建议一个国内、一个国外，例如 DeepSeek `deepseek-chat` 和通义千问 `qwen-plus`。测之前写下模型名和日期，因为模型会更新。

## 3. 样本

- 用 `asr-evaluation.md` §3 的同一套录音，至少一段 5 分钟、一段 30 分钟，其中一段有 ≥ 3 人对话。
- **输入用人工校对过的参考文字稿**，不用某个引擎的转写结果。这样分出来的差别只来自提示词和模型，不混进转写错误。另外再用最终选定的转写引擎的输出跑一遍主选方案，看转写错误会让纪要差多少。
- 30 分钟那段会走「长文字稿先分段压成要点、再整理」的路径（`Summarizer` 的分段逻辑），要单独看它有没有漏掉中间的内容。
- 和转写评估一样，录音、文字稿和生成的纪要都不入库（硬规则 4；这些是别人的谈话内容）。入库的只有评分表和汇总结果。

## 4. 怎么生成、怎么打分

1. **生成**：每个「样本 × 提示词 × 模型」生成一次，结果存成文件，文件名用随机编号（例如 `o17.md`），不带模型名和提示词名。编号与模型、提示词的对应关系另存为 `key.csv`，打分结束前不给打分人看。用 `client/summary_generate.py` 一次做完：

```bash
cd client
export DEEPSEEK_API_KEY=…   # 密钥只从环境变量读，不写在命令里
python summary_generate.py --transcripts eval/refs --out eval/blind \
    --prompt B=prompts/b-beanpod.txt --prompt C=prompts/c-plain-minutes.txt \
    --model deepseek-chat=https://api.deepseek.com/v1,deepseek-chat,DEEPSEEK_API_KEY \
    --existing A@deepseek-chat=eval/exports-a --scorers 甲,乙
```

   - 都放在 `client/eval/` 下（在 `.gitignore` 里，文字稿和纪要不会被误提交）。
   - 输出：`eval/blind/o01.md`…，`key.csv`，`timing.csv`（每次生成的秒数），以及 `scores-template.csv`（每个输出、每个打分人一行，分数空着，填好就是第 2 步的 `scores.csv`）。
   - 失败的组合（例如服务商限流）会列出来，不进入这一套；目录里已有一套时拒绝写入，免得混在一起。
   - 提示词 A：在 App 里跑。把参考文字稿存成 `.txt` 导入（E2），生成纪要，导出 Markdown，按样本名存进一个目录（`eval/exports-a/m30.md`），用 `--existing A@模型名=目录` 放进同一套。`--existing` 的模型名要和 `--model` 里同一个模型的名字一致，汇总时才会归到一起。
   - 提示词 B：beanpod 原版在它的仓库里（`0d00fab` 的 `Shared/Analyzer.swift` `analyze`），已按 MIT 许可复制进 `client/prompts/b-beanpod.txt`（2026-11-25），按默认取值展开：自动判断场景、职业「通用」、简体中文；文件头写明出处，`summary_generate.py` 读入时去掉开头的「# 」说明行，不发给模型（#68）。
   - 提示词 C：`client/prompts/c-plain-minutes.txt`，本项目写的，不分场景，字段用 App 的格式（`title`、`summary`、`sections`、`todos`），这样「能否解析」一栏三套可以比。
   - 参考文字稿会发给所选的服务；只用可以发给它们的材料。
2. **打分**：每个输出最好由两个人分别打分，每人在 `scores.csv` 里写一行：

| 列 | 取值 | 怎么判 |
|---|---|---|
| `fabrications` | 0、1、2… | 文字稿里找不到依据的说法有几条（包括「没有异议」「已达成一致」这类推断）。**有一条就算这个输出不合格**，其他分再高也不行 |
| `coverage` | 1～5 | 结论、决定、重要数字有没有漏。5：都在；3：漏了次要的；1：漏了主要结论 |
| `todos` | 1～5 | 待办是否齐全、谁做、什么时候。5：齐全且责任人和时间都对；1：大部分漏了或张冠李戴 |
| `structure` | 1～5 | 场景判断对不对，栏目是否合适，标题是否说得出这次在谈什么 |
| `concision` | 1～5 | 有没有废话、重复，长度是否和录音长度相称 |
| `parsed` | 0、1 | 回复能否按 App 的格式读出来（JSON 有效、该有的字段都在）。0 表示 App 里会显示「服务的回复看不懂」 |

3. **汇总**：

```bash
cd client
python summary_scores.py eval/blind/scores.csv eval/blind/key.csv
```

   - 按「模型 × 提示词」分组，输出评分次数、样本数、有编造的次数、解析失败的次数、四项的平均分和总平均。
   - 排序：先按有编造的次数从少到多，再按总平均从高到低。
   - 加 `--json` 得到明细。

4. **另外记**：每次生成的耗时，以及按服务商价格算的单次费用。

## 6. 判据与结论（待测后填写）

- **默认方案**：有编造的次数为 0 的组合里，总平均最高的；差距在 0.3 分以内时，选更便宜、更快的。
- **提示词 B 的去留**：如果 B 不比 A 好，在 #68 里写明原因并关闭；如果 B 在某一项明显更好，把那一部分改进 A。
- **长录音**：30 分钟样本上覆盖分明显低于 5 分钟样本时，调整分段压缩的做法（`Summarizer` 的分段长度和压缩提示词）。
- 结论写进 #12；后端搭起来后，提示词按 #68 移到服务端，App 和后端用同一份。
