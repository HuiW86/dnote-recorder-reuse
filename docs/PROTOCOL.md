# 追觅 D·NOTE 录音卡 BLE 协议规格

**适用型号**　DNOTE001B（追觅 D·NOTE AI 录音名片）
**来源**　逆向自官方 DreameNote App（`com.dnote.dreame`，Capacitor/JavaScript 实现）
**用途**　脱离官方 App 与追觅云，直接通过蓝牙控制录音卡、取回录音

---

## 1. 协议定位

录音卡本身只负责录音、存储与传输；转写、总结等能力由 App 与云端承担。设备侧的全部可控能力通过一条 BLE 私有服务暴露，命令集完整、无加密握手，连接与文件读取不以云端绑定为前提。因此在官方账号体系失效（短信验证码停发）的情况下，仍可完全离线复用硬件。

## 2. 链路层

### 2.1 GATT 服务

| 角色 | UUID | 属性 |
|---|---|---|
| Service | `00006001-0000-1000-8000-00805f9b34fb` | — |
| 写特征 | `00006002-0000-1000-8000-00805f9b34fb` | Write / WriteWithoutResponse |
| 通知特征 | `00006003-0000-1000-8000-00805f9b34fb` | Notify |

命令经写特征下发，设备响应与数据经通知特征上报。固件升级帧使用 WriteWithoutResponse，其余使用带响应写。

### 2.2 广播

厂商数据公司 ID 为 `0x22A3`（十进制 8867）；广播同时携带 SIG 成员 service UUID `FE98`。广播体结构（公司 ID 之后，大端）：

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0–1 | CID | 固定 8867，不符则非本设备 |
| 2–3 | BID | 品牌 ID |
| 4–5 | PID | 产品 ID |
| 6–7 | 固件版本 | `v{major}.{minor}` |
| 8–9 | 硬件版本 | `v{major}.{minor}` |
| 10 | 电量 | 百分比 |
| 11 | 电源状态 | 0 未知 / 1 仅电池 / 2 仅充电 / 3 仅放电 / 4 旁路 |
| 12–14 | SID | 24 位设备标识 |

实测（iOS 27.2，#7）：iOS 收到的广播只有厂商数据、本地名 `D·NOTE` 和可连接标志，**不含服务 UUID 列表**（`FE98` 与 `6001` 均不在其中），因此按服务过滤的扫描（iOS 后台扫描的前提）发现不了本设备。设备被连接期间不广播。证据 `evidence/v7-ios/`。

## 3. 帧结构

所有命令与响应共用定长头部：

```
[PID=0xA0] [CMD] [LEN] [PAYLOAD ...]
```

- `PID` 固定 `0xA0`，用于帧有效性校验
- `CMD` 命令字
- `LEN` 单字节，PAYLOAD 长度（0–255）
- 无帧校验和；依赖 BLE 链路层保证完整性

PAYLOAD 编码分三类：多数命令为 UTF-8 JSON；开关类为单字节 `0x00/0x01`；文件数据与绑定信息为二进制结构（见 §5、§6）。

## 4. 命令集

### 4.1 查询与设置

| CMD | 名称 | PAYLOAD | 响应 |
|---|---|---|---|
| 0x80 | 查询设备信息 | — | JSON `{sn, btaddr, bt, recmode, ...}` |
| 0x81 | 查询开关状态 | — | JSON |
| 0x82 | USB 存储开关 | `[0\|1]` | — |
| 0x83 | LED 开关 | `[0\|1]` | — |
| 0x84 | 马达开关 | `[0\|1]` | — |
| 0x85 | 降噪开关 | `[0\|1]` | — |
| 0x86 | 设置蓝牙名 | JSON `{bt}` | — |
| 0x87 | 校准时间 | JSON `{time:"YYYYMMDDHHmmss"}` | — |
| 0x88 | WiFi 热点配置 | JSON `{ap, ssid, psk}` | — |
| 0x89 | WiFi STA 上传地址 | JSON `{url}` | — |
| 0x8A | 保存 WAV 开关 | `[0\|1]` | — |
| 0x8B | VAD 开关 | `[0\|1]` | — |
| 0x8C | 增益档位 | `[1..9]` | — |
| 0x8D | 降噪档位 | `[1..9]` | — |
| 0x8F | 空闲关机时长 | uint32 大端（秒） | — |

`0x88` 的官方用法（WiFi 快传，官方 JS `FastTransferWifi`）：每次快传生成 12 位随机密码，发 `{ap:1, ssid:"FastUpload", psk}` 开热点，结束时发 `{ap:0, ...}` 关闭；`0x80` 的 `wifiap` 字段反映热点开关。

### 4.2 文件管理

| CMD | 名称 | PAYLOAD | 响应 |
|---|---|---|---|
| 0x90 | 列出文件 | — | 逐条 JSON `{index, name, size, end}`，`end=1` 结束 |
| 0x91 | 删除文件 | JSON `{name}` | — |
| 0x92 | 查询文件大小 | JSON `{name}` | JSON |
| 0x93 | 恢复出厂 | — | — |
| 0x94 | 格式化存储 | — | — |
| 0x95 | 关机 | — | — |

### 4.3 录音控制

| CMD | 名称 | PAYLOAD | 响应（固件 v1.50 实测） |
|---|---|---|---|
| 0x50 | 停止录音 | — | `0x50 [01]`，随后推送 `0x56 {rec:0}` |
| 0x51 | 开始录音 | `[0]` 普通录音；`[1]` 录音并实时推流 | `0x51 {"name":"YYYYMMDDHHmmss.opus"}`；`[1]` 时约 0.5 s 后开始推送 `0x68`（§5.1） |
| 0x52 | 暂停 | — | 未测 |
| 0x53 | 继续 | — | 未测 |
| 0x54 | 开始实时录音 | `[0\|1]` | 单独发送无响应、无 `0x68`、不断开；实时流不依赖它 |
| 0x56 | 查询录音状态 | — | JSON `{name, size, recd, rec, upload}`，`rec` 0 空闲 / 1 录音中 |

> 官方 App 的实时流程：发 `0x51 [1]`；500 ms 内没收到 `0x68` 再补发 `0x54 [1]`；每收到 `0x54` 通知就再发一次 `0x54 [1]`。实测 `0x51 [1]` 已足够，`0x54` 只是兜底（#4 V1，`evidence/v1-live/`）。

设备主动推送（固件 v1.50，#7 实测，前台、后台、锁屏一致）：按键开始录音时推送 `0x54` `{name}`（新文件名）；按键停止或收到 `0x50` 后推送 `0x56` 录音状态（`rec:0`）和空载荷的 `0x55`；连接期间约每 4 分钟推送一次 `0x80` 设备信息。客户端可据 `0x56 rec:0` 触发文件列表刷新。

### 4.4 绑定与加密

| CMD | 名称 | PAYLOAD |
|---|---|---|
| 0xA0 | 绑定 | `[1]` + 16 字节 bondId；解绑为 `[0]` |
| 0xA1 | 查询绑定 | — → `{isBonded, bondId}` |
| 0xA2 | 设置 ChaCha20 密钥 | `[enable]` + 32 字节 key |
| 0xA3 | 查询加密状态 | — |

### 4.5 固件升级

| CMD | 名称 | PAYLOAD |
|---|---|---|
| 0xB0 | 启动升级 | `[2]` |
| 0xB1 | 传输固件数据 | `[flag]` + offset(uint32 BE) + 数据 |

## 5. 文件下载流程（0x70）

下载为分片拉取，由一条启动命令触发，数据经通知连续上报：

启动：`0x70`，PAYLOAD 为 JSON `{cmd:1, name, offset:0}`。

每个数据通知的 PAYLOAD 结构：

```
[start(1)] [offset(4, 大端)] [data ...]
```

`start` 高 4 位（`start & 0xF0`）为状态位：

| 值 | 含义 |
|---|---|
| 0x20 | EOF，传输完成 |
| 0x30 | 已取消 |
| 0x40 | 错误 |
| 0xF0 | 文件不存在 |

接收方按到达顺序拼接 `data`，收到 EOF 即组装完成。

> 原版 App 在下载完成后会自动删除设备文件（0x91）。离线客户端默认不删除，仅在显式要求时删除。

### 5.1 实时音频流（0x68）

`0x51 [1]` 启动后，设备在录音的同时经通知推送 `0x68`，直到收到 `0x50`。每条通知（实测固定 168 字节）：

```
[0xA0][0x68][LEN=0xA5] [flag|seq(1)] [offset(4, 大端)] [Opus 数据 160 字节 = 4 帧]
```

| 字段 | 说明 |
|---|---|
| flag | 第 1 字节高 4 位：首包 0，之后 1 |
| seq | 第 1 字节低 4 位：0～15 循环 |
| offset | 本包音频在流中的字节偏移，每包 +160；不连续即丢包 |

- 约 12.5 包/秒 = 50 帧/秒 ≈ 2 KB/s，与 20 ms/帧一致；60 s 实测帧数偏差 0.14%～0.15%，连续 3 次无断开。
- **明文**：音频为裸 Opus（格式同 §6.1），不受 §6.2 加密影响，可直接解码。
- 卡上同时以加密文件保存同一段录音；解密后与实时流逐帧一致（实时流尾部多约 0.4 s 未写入文件）。
- 停止后普通录音（`0x51 [0]`）与文件列表（`0x90`）正常。

## 6. 音频格式与解密

### 6.1 编码

设备输出为**裸 Opus 帧流**：16 kHz、单声道、20 ms/帧、定长 **40 字节/帧**。客户端按 40 字节顺序切帧，再封装为标准 OGG（OpusHead `preSkip=312`、granule 以 48 kHz 计 960/帧）。

### 6.2 加密（可选）

若设备启用加密，下载得到的文件以 ASCII `encryt` 开头。密钥派生**完全离线**，不依赖云端：

```
key = HMAC-SHA256(DEVICE_KEY_SECRET, sn)      # sn 为设备序列号
```

`DEVICE_KEY_SECRET` 为 32 字节常量，硬编码于 App（见 `dnote_protocol.py`）。文件布局与解密：

| 偏移 | 内容 |
|---|---|
| 0–5 | magic `encryt` |
| 0–23 | 头 24 字节（解密后用于校验） |
| 6–23 | 18 字节派生料（作为上式 `sn` 之外的 HMAC 输入） |
| 24–35 | 12 字节 ChaCha20 nonce |
| 36–59 | 24 字节校验块（密文） |
| 60– | 音频密文 |

解密：`明文 = ChaCha20(key, nonce, buf[36:60] + buf[60:])`，校验 `明文[0:24] == buf[0:24]`，返回 `明文[24:]`。

> 注：App 中密钥派生存在两处输入——绑定时以序列号派生并下发（0xA2），文件头又携带 18 字节派生料。客户端对两种来源均做兼容：文件解密以文件头派生料为准（§6.2 表），设备密钥设置以序列号为准。

## 7. WiFi 高速传输通道

BLE 实测约 24 KB/s（#5，Mac 23.60 KB/s；V7，iPhone 25.55 KB/s），15 MB 的两小时录音要 10 分钟左右。设备另提供 WiFi 快传，实测约 **780 KB/s**，同一文件约 19 s。

**来源**：命令集取自固件 `strings`（`recpen_file_server`，见 `docs/craft-anything-evaluation.md` §5.1）；线格式、帧结构与吞吐为真机实测（#6，证据 `evidence/v2-fasttransfer/`）。官方 App 的 JS 未用到。

### 7.1 建立通道

1. BLE 发 `0x88 {"ap":1,"ssid":"FastUpload","psk":<随机>}`，卡开热点（`0x80` 推送中 `wifiap` 变为 1）
2. 手机加入 `FastUpload`，拿到 `192.168.88.x` 地址；卡在 `192.168.88.1`
3. TCP 连 `192.168.88.1:6718`。连上后卡不主动发任何数据
4. 用完后 BLE 发 `0x88 {"ap":0,...}` 关热点

iOS 上首次加入会弹系统确认框，须人工批准一次（#21）。实测加入要 45–80 s，比传输本身还长。

### 7.2 请求

纯文本命令，不需要结束符（`list_files`、`list_files\n`、`list_files\r\n` 回包相同）。一条连接上可以连发多条。

| 命令 | 作用 | 状态 |
|---|---|---|
| `list_files`（固件也认 `list`） | 列出 `/sdcard/record` 下的 `.opus` | 已验证 |
| `get <文件名>` | 卡把文件发给手机（**下载**） | 已验证 |
| `pull <文件名>` | 卡从手机接收文件（**上传**到卡） | 未验证；对 `pull <已有文件>` 卡回 `status=01` |
| `delete <文件名>` | 删除 | 未验证（会写卡） |
| `quit` | 结束会话 | 未验证 |

注意 `pull` 是上传，不是下载（固件日志 `pull_file %s` → `pull start` → `pull:%d`；下载侧的日志是 `send_file %s` → `send offset:%d,size:%d,total:%d`）。

### 7.3 回包帧

```
[0xAA] [TYPE] [STATUS] [LEN u16 大端] [BODY ...]
```

| TYPE | 含义 |
|---|---|
| `0x00` | 列表项 |
| `0x01` | 文件块 |
| `0x04` | `pull` 的回复 |
| `0x05` | 未知命令（`STATUS=01`，无 BODY） |

`STATUS=00` 为成功，`01` 为失败。多字节整数除 `LEN` 外都是小端。

### 7.4 列表（TYPE `0x00`）

每个文件一帧，BODY 为 `index u32 | total u32 | size u32 | name（NUL 结尾）`，`index` 从 1 起。
最后一帧是结束哨兵：`name="0"`、`size=0`。内容与 BLE `0x90` 列表一致。

### 7.5 下载（TYPE `0x01`）

每块一帧，BODY 为：

```
total u32 | offset u32 | chunk u32 | tag 2B | data[chunk]
```

- `chunk` 实测为 8192，最后一块为余数；`offset + chunk == total` 即结束
- `data` 拼起来就是卡上的原文件，与 BLE `0x70` 下载的字节完全相同（加密文件仍需按 §6.2 解密）
- `tag` 每块不同，像校验值，但不是常见的 CRC16，算法未知。完整性靠 TCP 和整文件 sha256 保证

## 8. 认证模型结论

- **连接与读取不以绑定为门禁**：App 中 `bondDevice` 调用被 `.catch(()=>{})` 吞错，绑定仅用于云账号登记与会员能力。
- **bondId 来自云端**：由 `postRecorderActive` 返回的 `code` 取前 16 字节；离线场景不需要。
- **加密密钥可离线推导**：仅依赖硬编码常量与设备序列号/文件头派生料，无需云端。

因此 L2（自研客户端，设备功能全保留）可完全脱离官方 App 与追觅云实现。
