# 追觅 D·NOTE 录音卡 BLE 协议规格

**适用型号**　DNOTE001B（追觅 D·NOTE AI 录音名片）
**来源**　逆向自官方 DreameNote App（`com.dnote.dreame`，Capacitor/JavaScript 实现）
**用途**　脱离官方 App 与追觅云，直接通过蓝牙控制录音卡、取回录音

---

## 1. 协议定位

录音卡本身只负责录音、存储与传输；转写、总结等能力由 App 与云端承担。设备侧的全部可控能力通过一条 BLE 私有服务暴露，命令集完整、无加密握手，连接与文件读取不以云端绑定为前提。因此在官方账号体系失效（短信验证码停发）的情况下，仍可完全离线复用硬件。

## 2. 链路层

### 2.1 GATT 服务

| 角色 | UUID | 属性 |
|---|---|---|
| Service | `00006001-0000-1000-8000-00805f9b34fb` | — |
| 写特征 | `00006002-0000-1000-8000-00805f9b34fb` | Write / WriteWithoutResponse |
| 通知特征 | `00006003-0000-1000-8000-00805f9b34fb` | Notify |

命令经写特征下发，设备响应与数据经通知特征上报。固件升级帧使用 WriteWithoutResponse，其余使用带响应写。

### 2.2 广播

厂商数据公司 ID 为 `0x22A3`（十进制 8867）；广播同时携带 SIG 成员 service UUID `FE98`。广播体结构（公司 ID 之后，大端）：

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0–1 | CID | 固定 8867，不符则非本设备 |
| 2–3 | BID | 品牌 ID |
| 4–5 | PID | 产品 ID |
| 6–7 | 固件版本 | `v{major}.{minor}` |
| 8–9 | 硬件版本 | `v{major}.{minor}` |
| 10 | 电量 | 百分比 |
| 11 | 电源状态 | 0 未知 / 1 仅电池 / 2 仅充电 / 3 仅放电 / 4 旁路 |
| 12–14 | SID | 24 位设备标识 |

## 3. 帧结构

所有命令与响应共用定长头部：

```
[PID=0xA0] [CMD] [LEN] [PAYLOAD ...]
```

- `PID` 固定 `0xA0`，用于帧有效性校验
- `CMD` 命令字
- `LEN` 单字节，PAYLOAD 长度（0–255）
- 无帧校验和；依赖 BLE 链路层保证完整性

PAYLOAD 编码分三类：多数命令为 UTF-8 JSON；开关类为单字节 `0x00/0x01`；文件数据与绑定信息为二进制结构（见 §5、§6）。

### 4.4 绑定与加密

| CMD | 名称 | PAYLOAD |
|---|---|---|
| 0xA0 | 绑定 | `[1]` + 16 字节 bondId；解绑为 `[0]` |
| 0xA1 | 查询绑定 | — → `{isBonded, bondId}` |
| 0xA2 | 设置 ChaCha20 密钥 | `[enable]` + 32 字节 key |
| 0xA3 | 查询加密状态 | — |

> 实测（固件 v1.50）：设置类命令以 `[0x01]` 表示成功、`[0x00]` 表示失败。`0x51` 响应为 JSON `{name}`，`name` 为 `"NULL"` 表示设备拒绝开始录音；成功时为 `YYYYMMDDHHmmss.opus`。`0x90` 每条一帧，结束帧为 `{name:"", size:0, index:N, end:1}`。未配对时 `0x90` 不响应、`0x51` 回 `NULL`、`0x94` 回 `0x00`，见 §8。

| 0xB1 | 传输固件数据 | `[flag]` + offset(uint32 BE) + 数据 |

## 5. 文件下载流程（0x70）

下载为分片拉取，由一条启动命令触发，数据经通知连续上报：

启动：`0x70`，PAYLOAD 为 JSON `{cmd:1, name, offset:0}`。

每个数据通知的 PAYLOAD 结构：

```
[start(1)] [offset(4, 大端)] [data ...]
```

`start` 高 4 位（`start & 0xF0`）为状态位：

| 值 | 含义 |
|---|---|
| 0x20 | EOF，传输完成 |
| 0x30 | 已取消 |
| 0x40 | 错误 |
| 0xF0 | 文件不存在 |

接收方按到达顺序拼接 `data`，收到 EOF 即组装完成。

> 原版 App 在下载完成后会自动删除设备文件（0x91）。离线客户端默认不删除，仅在显式要求时删除。

## 6. 音频格式与解密

### 6.1 编码

设备输出为**裸 Opus 帧流**：16 kHz、单声道、20 ms/帧、定长 **40 字节/帧**。客户端按 40 字节顺序切帧，再封装为标准 OGG（OpusHead `preSkip=312`、granule 以 48 kHz 计 960/帧）。

### 6.2 加密（可选）

若设备启用加密，下载得到的文件以 ASCII `encryt` 开头。密钥派生**完全离线**，不依赖云端：

```
key = HMAC-SHA256(DEVICE_KEY_SECRET, sn)      # sn 为设备序列号
```

`DEVICE_KEY_SECRET` 为 32 字节常量，硬编码于 App（见 `dnote_protocol.py`）。文件布局与解密：

| 偏移 | 内容 |
|---|---|
| 0–5 | magic `encryt` |
| 0–23 | 头 24 字节（解密后用于校验） |
| 6–23 | 18 字节派生料（作为上式 `sn` 之外的 HMAC 输入） |
| 24–35 | 12 字节 ChaCha20 nonce |
| 36–59 | 24 字节校验块（密文） |
| 60– | 音频密文 |

解密：`明文 = ChaCha20(key, nonce, buf[36:60] + buf[60:])`，校验 `明文[0:24] == buf[0:24]`，返回 `明文[24:]`。

> 注：App 中密钥派生存在两处输入——绑定时以序列号派生并下发（0xA2），文件头又携带 18 字节派生料。客户端对两种来源均做兼容：文件解密以文件头派生料为准（§6.2 表），设备密钥设置以序列号为准。

## 7. WiFi 高速传输通道

BLE 全速约 1 MB/s。设备另提供 WiFi 快传：开启后广播热点 `FastUpload`，设备地址 `192.168.88.1`，TCP 端口 `6718`。大文件批量回传时优于 BLE。本规格的离线客户端当前实现 BLE 通道，WiFi 通道为后续扩展项。

## 8. 认证模型结论（2026-11-05 真机修订）

- **设备固件有配对门禁**：未配对时仅查询类（0x80/0x81/0x56/0xA1/0xA3）与简单设置（0x82/0x87 等）可用；录音、文件列表、格式化被拒。早先"连接与读取不以绑定为门禁"的结论只对 App 侧成立（App 吞掉了 `bondDevice` 的错误）。
- **App 的绑定流程**（`DeviceScan-*.js` + `bindNewDevice`）：连接 → `0x94` 格式化 → `0x80/0x81/0x56/0x87` → 云端 `postRecorderActive` 取 `code` → `0xA2 [1]+deriveDeviceKey(sn)` → `0xA1/0xA3` → `0xA0 [1]+code[0:16]`。
- **bondId 不校验来源**：本地随机 16 字节即可绑定成功。
- **加密密钥可离线推导**：仅依赖硬编码常量与设备序列号/文件头派生料，无需云端。

**离线配对**：`0xA2 [1]+HMAC-SHA256(DEVICE_KEY_SECRET, sn)` → `0xA0 [1]+本地 bondId` → **断开重连**后生效（同一连接内不生效；生效条件待复核，见 HANDOFF §5.2）。

因此 L2（自研客户端，设备功能全保留）可完全脱离官方 App 与追觅云实现，已在真机验证录音→列表→下载→解密全链路。
